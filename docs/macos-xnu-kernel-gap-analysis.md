# macOS XNU kernel features missing or incomplete in Vinix

Date: **2026-10-02**. This report compares Apple's latest publicly published macOS XNU source with the current Vinix kernel, grouped by security, syscalls/processes/IPC, virtual memory, scheduling/performance, filesystems/storage, networking, hardware/power, and observability. The report contains **49 findings**. Findings describe source-level capability gaps, incomplete semantics, and architectural differences. They do not establish that XNU is faster or that every Darwin interface should be added to Vinix.

## Method and status labels

The review read implementations in both downloaded XNU and Vinix, checked syscall registration and supplemental overrides on both architectures, and examined relevant build configuration and tests. Existing reports were used as navigation aids, then checked against current code. An accepted flag, saved setting, syscall slot, or bundled dependency was not counted as an implemented behavior by itself.

- **Missing:** no equivalent behavior found in the relevant Vinix subsystem and callers inspected.
- **Partial:** an equivalent facility exists, but the named behavior is missing.
- **Stub:** the interface accepts or reports state without implementing the named effect.
- **Architectural:** Darwin-specific machinery absent from Vinix's intentionally Linux-oriented kernel; adding its ABI is optional.
- **Backend-dependent:** XNU implements a dispatch/control interface, but the actual service requires a filesystem, driver, hardware feature, or external policy provider.

Priorities: **P1** = enforcement, correctness, or a common current workload; **P2** = useful expansion or a measured optimization; **P3** = optional architecture/product capability. These are recommendations. This was a static source comparison: no XNU build, Vinix kernel modification, runtime security experiment, or comparative benchmark was performed.

## Existing Vinix features excluded from the gap list

Vinix already provides a substantial foundation:

- Security: pledge, unveil, seccomp filters, default W^X, user ASLR, stack canaries, checked user copies, immutable mappings/files, signed signal frames, a reseeded kernel PRNG, Linux capabilities, and architecture-specific page/access protections. See [security overview](security.md), [OpenBSD-derived defenses](openbsd-security.md), [seccomp](../kernel/proc/seccomp.v), and [filesystem permissions](../kernel/fs/permissions.v).
- Memory/scheduling: demand paging, fork copy-on-write, LRU/indexed block caching with clean-page reclaim, NUMA placement, affinity, FIFO/RR/deadline policies, and cgroup CPU/memory accounting and OOM handling. See [VM](../kernel/memory/mmap/mmap.v), [cache](../kernel/pagecache/pagecache.v), [NUMA](numa.md), [real-time scheduling](realtime.md), and [cgroups](../kernel/fs/cgroup.v).
- Syscalls/IPC/storage: Linux ABI tables on amd64/arm64, clone/clone3, namespaces, resource-limit APIs, Unix descriptor passing, pipes, epoll, inotify, eventfd/signalfd/timerfd, POSIX wall-clock timers, SysV shared memory/semaphores, sendfile/splice/tee/copy_file_range, writable EXT2, sparse tmpfs, overlay, shared file mappings, fsync/msync, and background block-cache writeback. See [amd64 table](../kernel/syscall/table/linux_table_amd64.v), [arm64 table](../kernel/syscall/table/syscall_table_arm64.v), [additional calls](../kernel/syscall/table/gaps.v), and [EXT2 mapped pages](../kernel/fs/ext2/mapping.v).
- Hardware: IPv4 TCP/UDP through lwIP, VirtIO/e1000 and Apple Wi-Fi paths, Intel VT-x virtualization, Apple DART mappings, Apple power-domain control, and device-specific display hotplug. These are present facilities with narrower scope than their XNU counterparts. See [network configuration](../kernel/c/lwipopts.h), [hypervisor](hypervisor.md), [DART](../kernel/apple/dart/dart.v), [PMGR](../kernel/aarch64/pmgr/pmgr.v), and [display hotplug](../kernel/c/apple_display_hotplug.c).
- Allocator: an optional, adapted XNU zone/magazine backend already exists. Its [port status](xnualloc/PORT_STATUS.md) explicitly describes missing typed heaps, read-only zones, VM integration, and scalable locking. The gap is completion and integration, rather than absence of every XNU allocator idea.

## Security

The public macOS configuration selects MACF and audit through [ARM64 SECURITY_BASE](https://github.com/apple-oss-distributions/xnu/blob/ac9718fb1af618d5ce8678d0dc6e8a58f252216f/config/MASTER.arm64.MacOSX#L99) and [x86 SECURITY](https://github.com/apple-oss-distributions/xnu/blob/ac9718fb1af618d5ce8678d0dc6e8a58f252216f/config/MASTER.x86_64#L69); these map to [CONFIG_MACF/CONFIG_AUDIT options](https://github.com/apple-oss-distributions/xnu/blob/ac9718fb1af618d5ce8678d0dc6e8a58f252216f/config/MASTER#L567). Whether a policy or collector is active remains a separate question.

| --- | --- | --- |
| PERF1 — Partial, P2 | **CPU-local allocator fast paths.** XNU [zone cache protocol](https://github.com/apple-oss-distributions/xnu/blob/ac9718fb1af618d5ce8678d0dc6e8a58f252216f/osfmk/kern/zalloc.c#L274) separates local magazines and locked depots. | PERF2 — Partial, P2 | **Run-queue scalability.** XNU [Clutch processor/processor-set queues](https://github.com/apple-oss-distributions/xnu/blob/ac9718fb1af618d5ce8678d0dc6e8a58f252216f/osfmk/kern/sched_clutch.c#L3426) supplies distributed queue structures. | PERF3 — Missing QoS / partial priorities, P2 | **Coordinated workload QoS.** XNU [thread QoS policy](https://github.com/apple-oss-distributions/xnu/blob/ac9718fb1af618d5ce8678d0dc6e8a58f252216f/osfmk/kern/thread_policy.c#L78) combines CPU priority, I/O tier, latency, and throughput hints; Clutch tracks interactivity. | PERF4 — Missing, P2 | **Heterogeneous core placement.** XNU [Edge processor selection](https://github.com/apple-oss-distributions/xnu/blob/ac9718fb1af618d5ce8678d0dc6e8a58f252216f/osfmk/kern/sched_clutch.c#L6062) selects preferred cluster sets by QoS/load. | PERF5 — Missing, P1 | **Blocking-lock priority inheritance.** XNU [turnstile inheritance](https://github.com/apple-oss-distributions/xnu/blob/ac9718fb1af618d5ce8678d0dc6e8a58f252216f/osfmk/kern/turnstile.c#L1506) and [user locks](https://github.com/apple-oss-distributions/xnu/blob/ac9718fb1af618d5ce8678d0dc6e8a58f252216f/bsd/kern/sys_ulock.c#L736) propagate waiter priority to owners. | PERF6 — Partial, P1 | **Priority-driven busy-CPU preemption on ordinary enqueue.** XNU [sched_ipi_action/perform](https://github.com/apple-oss-distributions/xnu/blob/ac9718fb1af618d5ce8678d0dc6e8a58f252216f/osfmk/kern/sched_prim.c#L4421) requests preemption as well as idle wake. ## Recommended implementation order

| Order | Work | Reason and acceptance evidence |
| --- | --- | --- |
| 1 | Make accepted restrictions and settings reliable: mount flags, W^X exceptions, CPU timers/limits, dumpability, routing control. | Callers must be able to trust success. Add behavioral tests showing the restriction/expiry/state change, on amd64 and arm64; unsupported behavior should return an error. |
| 2 | Establish memory-pressure reserve/reclaim/OOM policy and physical storage flush/error contracts. | These protect desktop workload continuity and stored data. Test bounded low-memory behavior, dirty-write retry, flush failures, and storage ordering. Treat shared mmap coherence as already implemented. |
| 3 | Add debugger/core support, truthful resource accounting, and basic tracing/profiling. | These make the next correctness and performance projects diagnosable. Verify stopped-thread lifetimes, sensitive-data policy, buffer overflow reporting, and tool compatibility. |
| 4 | Add IPv6, real multi-interface/routing configuration, firewall hooks, and TUN. | These unlock practical workstation/container/VPN use. Test packet paths and namespace ownership, rather than accepting configuration commands alone. |
| 5 | Complete PI and busy-CPU rescheduling; then pressure-aware paging and measured allocator/TLB/run-queue scaling. | Preserve existing RT/COW/NUMA behavior while closing latency/pressure gaps. Measure before/after using identical hardware and workload; stress teardown, cancellation, reclaim, and SMP invalidation. |
| 6 | Build coordinated laptop suspend/runtime-power support. | Validate a complete quiesce/wake cycle on one platform before broad driver coverage or hibernation. |
| 7 | Decide product requirements for signed/verified systems, mandatory policy, snapshots, vouchers, and user workloops. | These require ABI, trust, filesystem, or service designs. Darwin-specific architecture should follow a concrete Vinix use case. |

## Validation and follow-up

This report is based on inspected source, not tests of a newly implemented kernel feature. The download was verified against Apple's Git objects; report links and paths were checked locally. Independent second reviews checked accepted mount restrictions, caller-controlled W^X exceptions, CPU TLB tagging, priority-driven enqueue notifications, and the storage/network/power findings. Static absence findings are scoped to the named implementations and registration paths. They are not proofs that no similarly named code exists anywhere, or demonstrations of an exploitable vulnerability.

For follow-up work, use existing [desktop performance scenarios](../tests/desktop-perf/run.py), [memory tests](../tests/memory/README.md), [real-time tests](../tests/realtime/README.md), [network tests](../tests/network/README.md), and [page-cache tests](../tests/pagecache/README.md). Measure allocation retention and validate new lifetimes as required by [AGENTS.md](../AGENTS.md); VM/allocator changes need independent lifetime review. Benchmark matched hardware/configurations before asserting a speedup. Keep amd64 and arm64 syscall behavior explicit and test both when shared semantics change.

Their dates and baselines differ from this report; they are not substitutes for its source checks.
