# Explicit musl loader and low fixed executables

Maps334 executed musl directly, and the kernel selected PIE base `0x400000`.
The unchanged native target is ET_EXEC with a LOAD range starting at
`0x400000`. Musl could not reserve that fixed address and exited with
`Not a valid dynamic program`. The trace and musl mapping path are recorded
in `tests/native-android-ws/maps334.md` at the source base below.

The PIE floor is now 256 MiB, retaining the existing 1 GiB interpreter
boundary and 2 MiB alignment. The actual production picker is extracted by
the host regression. Deterministic entropy reproduces the collision with
the old 2 MiB floor and avoids it with the new floor. Every entropy slot for
1 MiB and 28 MiB images is checked, together with RNG failure and the
unchanged oversized-image fallback. This change does not claim to make
oversized images fit beneath the interpreter.

The host runner now retains assertions: this V compiler removes `assert`
under `-prod`, which made the old negative control pass incorrectly. Four
positive test files pass without `-prod`; the separate old-floor control
must fail with `PIE_FIXED_EXEC_COLLISION` before the runner passes.

Both clean kernel builds and both strict guest runs passed. The maintained
V guest retains the original synthetic ELF and real PIE/interpreter checks,
then directly executes musl against a dynamic ET_EXEC linked at `0x400000`.
Each guest required all three `ELF TEXT PASS` verdicts, including
`ELF TEXT PASS: direct musl ET_EXEC at 0x400000`.
