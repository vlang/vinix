## Account creation must reach a shared durable store

`ajrb.x(...)` (`ajrb.smali:8425`) is the concrete GMS account creation wrapper.
The aligned instruction scan of all fifteen APK DEX files finds one direct
four-argument `addAccountExplicitly(Account,String,Bundle,Map)` invocation,
through `alu$$ExternalSyntheticApiModelOutline0.smali:823`, and zero direct
three-argument invocations. Five callers of `ajrb.x` are retained in
`store-wrapper-callers.txt`; these include `akjj.a/e`, the actual auth-code and
long-lived session token account-add paths.

Immediately after insertion, `ajrb.x` does the following:

1. Calls `getAccountsByType` and verifies the new Account is present
   (`ajrb.smali:8612`, `cxly.smali:1651`). Absence logs an insertion failure and
   returns null. A fabricated successful return without storage cannot pass.
2. Calls `ajrb.q(Account,LST)` (`ajrb.smali:8729`). This first tries its own app
   storage and falls back to `setPassword` (`ajrb.smali:6610`, `cxly.smali:1029`).
   The password slot carries a long-lived session token in this flow.
3. Copies every string key/value in the initial Bundle through `setUserData`
   (`ajrb.smali:8783`, `cxly.smali:1124`). Initial metadata includes
   `GoogleUserId`; later GMS account enumeration filters out accounts whose Gaia
   identity metadata is missing (`ajrb.smali:3157`). Arbitrary bounded userdata
   storage is required.
4. If insertion returned false for an existing account, reapplies the package
   visibility map through `setAccountVisibility`.

The visibility map is generated by `ajqv.a` from `ajsh.b`, assigning every
allowlisted package value **2**, Android's `VISIBILITY_USER_MANAGED_VISIBLE`
(`aosp-AccountManager.java:315`). It reads package/version pairs from
`auth.account.visibility.whitelist.prefs` (`ajsf.smali`) and retains entries
whose installed package version still matches (`ajsh.smali:503`). This is
dynamic persisted state. The audited map producer has no static Maps entry;
no retained preferences snapshot establishes whether
`com.google.android.apps.maps` is currently included. Do not invent membership
or expose all stored accounts to every package.

The smallest storage increment therefore needs one broker-owned, restart-safe
store shared by authenticator and app VMs: account identity, password/LST,
userdata, visibility and removal. Mutations and secret reads must use the
registered authenticator authority for the account type. Implement both add
overloads against the same insertion semantics; the four-argument overload is
the demonstrated GMS path. Enumeration must apply the requesting package's
actual visibility policy. No claim here establishes current guest login.

## Token retrieval is a separate required increment

| Actual GMS operation | Retained callsite |
| --- | --- |
| `getPassword`, `getUserData` | `cxly.smali:379`, `:525` |
| `setPassword`, `setUserData` | `cxly.smali:1029`, `:1124` |
| `setAuthToken` | `ajrb.smali:6393` |
| `peekAuthToken` | `ajut.smali:786`, `boch.smali:795` |
| `invalidateAuthToken` | `cxly.smali:863`, `boch.smali:1197` |
| `getAuthToken` and timed future result | `babj.smali:198`, `:217` |

The actual manifest selects the enabled
`GoogleAccountAuthenticatorService` and authenticator resource `0x7f190008`.
Fresh `aapt2` output resolves this to `res/G21.xml` and records
`accountType="com.google"`, **`customTokens=true`**. Evidence is in
`authenticator-xml.txt` and `resource-map.txt`. `akgu.getAuthToken` returns
`authtoken` plus optional `android.accounts.expiry` in milliseconds
(`akgu.smali:8713`). A broker response cache keyed only by account/token type
would violate this authenticator's custom-token contract.

The next token increment should dispatch `getAuthToken` to the registered
authenticator without caching its responses initially. Preserve explicit
authenticator-owned `setAuthToken`/`peekAuthToken` storage and invalidation as
separate operations. A later custom-token response cache requires caller
package/signing identity and expiry, with tests for caller isolation.

`babj` intentionally passes null public API options. The AccountManager must
normalize these and inject trusted `callerUid` and `androidPackageName` before
dispatch: `akgu.getAuthToken` rejects null/empty options and reads those values
(`akgu.smali:7516`, `:7748`; `ajnk.smali:55`). The authenticator sets its own
`clientPackageName` to the GMS application package; that key does not identify
the requesting Maps package.

The six return sites in this APK's `akgu.addAccount` return copied Bundles via
`akgn.a`, including an interactive result retaining the original
`AccountAuthenticatorResponse` (`akgu.smali:3518`). No null return or direct
response callback was found in this override. Android's generic asynchronous
null-result contract still matters, but this inspection does not establish it
as the current GMS add-account failure.

## Validation needed for the next changes

- Reproduce the actual sequence: four-argument add, immediate enumeration,
  LST/password and userdata updates, duplicate add, visibility reapplication,
  process restart and enumeration from the Maps principal.
- Test unauthorized mutation/secret access and package visibility isolation,
  null userdata deletion, duplicate identity and crash-safe store replacement.
- Exercise explicit token set/peek/invalidate and getAuthToken dispatch with
  null public options, authenticated caller identity, real future completion,
  interactive result, cancellation and authenticator death.
- Reject cross-caller custom-token reuse; do not log credentials or tokens.

These are required test scopes, not completed login evidence. The audit ran no
guest, supplied no credentials and created no Google account.
