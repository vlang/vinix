# T6050 / G17C bring-up notes

Observations below are from a Mac17,6 with an Apple M5 Max running macOS 26.5
(25F71), AGXG17X 351.2. They are versioned facts, not assumptions that every
G17 machine has the same topology.

## Hardware identity

| Property | Observed value |
|---|---:|
| Apple DeviceTree compatible | `gpu,t6050` |
| GPU generation / variant | 17 / C |
| GPU cores | 40 |
| GPU partitions (`num_mgpus`) | 4 |
| Active dies (`arm-io` `die-count`) | 1 |
| Active PMP wrappers | 1 (`PMP0`) |
| Core masks | `0x3ff`, `0x3ff`, `0x3ff`, `0x3ff` |
| Fragment units | 40 |
| Geometry processors | 16 |

| System/GPU timestamp timebase | 24 MHz |

The two `sgx` register ranges reported by the Apple DeviceTree are
`0x2300000000 + 0x03fdc000` and `0x2300d00000 + 0x00177000`. Vinix must take
these from the boot-time device tree; they are recorded here only to make bad
hard-coded addresses obvious during review.

The corresponding `/arm-io/gfx-asc` node is `iop,ascwrap-v6`. Its first
register window is `0x2102600000 + 0x88000` before parent-bus translation.
The preloaded firmware mappings reported in `segment-ranges` are:

| Segment | Physical | RTKit IOVA | Size |
|---|---:|---:|---:|
| `__TEXT` | `0x10001000000` | `0xfffffc0000000000` | `0x4c000` |
| `__DATA` | `0x100026f0000` | `0xfffffc000004c000` | `0x130000` |

The ranges are virtually contiguous. The `__DATA` physical address and size
equal the independent `sgx` `gfx-data-base` and `gfx-data-size` properties.
`inspect_macos.py` now rejects drift in those relationships.

The native UAT reservations are also explicit in this tree: a `0x4000`-byte
handoff at `0x11ffff20000`, a `0x80000`-byte shared page-table region at
`0x11ffff28000`, and a `0x4000`-byte 64-context TTB table at
`0x11ffffa8000`. The `ttbat-phys-addr-base` value `0x47fffea` is exactly the
TTB physical base shifted right by the 14-bit UAT page size. G17 uses a
42-bit input address space (root/middle/leaf shifts `36/25/14`) and 16 KiB
table pages. Vinix now consumes these reserved regions and implements the
firmware's `0x648`-byte uPPL handoff structure instead of allocating an
unrelated page or treating AGX as a DART client.

The local AGXG17X 351.2 kernel implementation independently confirms the
handoff offsets. Its named `AGXUnifiedAddressTranslator::initHandoff` routine
writes `0x4b1d000000000002` at offset `0`, uses firmware magic at `0x8`, byte
locks at `0x10`/`0x11`, the turn at `0x14`, and the current slot at `0x18`.
It clears 65 24-byte flush records starting at `0x20`, followed by fields at
`0x638` and `0x640`. This is exactly `0x648` bytes; the surrounding reserved
page is larger. On a fresh handoff the Apple driver initializes the current
slot to `UINT32_MAX` and sets byte `0x638` when the firmware-side magic is not
already present. Firmware readiness remains a separate phase of bring-up.

## Device user-client ABI

An off-screen Metal triangle opens `AGXAcceleratorG17X` with type `0x100005`.
The AGX-specific selectors used during startup are:

| Selector | Kernel symbol | Input | Output |
|---:|---|---:|---:|
| `0x100` | `getDeviceConfig` | 0 | 152 bytes |
| `0x102` | `getDriverInfo` | 0 | 456 bytes |
| `0x105` | `performanceCounterSamplerControl` | 72 bytes | 72 bytes |
| `0x107` | `setDeviceNotificationPort` | async | 0 |

Selectors below `0x100` are implemented by the IOGPU superclass. The same
run queried selectors 0, 2, 5, and 6 with output sizes 64, 536, 32, and 16
bytes respectively. Run `make -f GNUmakefile trace` to reproduce the list on
the current operating system.

The `AGXDeviceUserClient::getTargetAndMethodForIndex` table also names
selectors through `0x112`; `agx_trace.c` annotates those names in JSON output.

## Metal command encoding

The installed userspace driver identifies the device as `AGXG17CDevice` and
uses `AGXG17XFamilyCommandQueue`, `AGXG17XFamilyCommandBuffer`, and
`AGXG17XFamilyRenderContext`. Its internal C++ templates select `HAL300`.

Private IOGPU storage calls bracket one 2,752-byte (`0xac0`) segment for both
an empty clear and the triangle. In a same-process pair only 50 bytes in 33
runs differ. The segment begins with `0x00000ac000010000` as a little-endian
64-bit word; disassembly of `AGX::ContextCommon<HAL300>::newCommand` agrees
that `0xac0` is the segment size. These observations are reproducible with
`make -f GNUmakefile trace`; they are not yet a complete work-command ABI.

Resource tracing resolves addresses in the segment only against allocations
already exposed to the process by `IOGPUMetalResource`. In the observed pair,
the clear references offset `0x400` and the triangle offset `0x100` in the same
32 KiB allocation. The two snapshots differ in 794 bytes. A triangle-only
128 KiB allocation is also referenced, consistent with pipeline/shader state.
The GPU virtual addresses are allocation-run observations, not constants to
copy into Vinix.

## Vinix userspace boundary

Vinix pins Mesa 25.0.5. Its Asahi interface is an explicitly unstable UAPI,
so `kernel/modules/drm/ioctl/ioctl.v` mirrors that version byte-for-byte: the
global parameter block is `0x1b0` bytes, a top-level command is `0x38`, and a
render command is `0x1d0`. The kernel validates every structure size before
registering an AGX DRM device. The core DRM path also supplies version,
capability, GEM-close, binary-syncobj, and GEM mmap services needed by libdrm.

This contract does not make Mesa 25.0.5 a G17 compiler. That Mesa release
selects only G13/G14 device backends and would mis-encode G17 as G14X. Vinix
therefore rejects real command submission with `EOPNOTSUPP`, and the T6050
firmware boot gate remains closed, until the HAL300 shader and work-command
encoders are recovered. The previous Vinix ioctl accepted a made-up compact
render structure unrelated to Mesa; it has been removed rather than exposed
to hardware.

## Firmware boundary

The G17 firmware is supplied by `AGXFirmwareKextG17XRTBuddy`, not by the
macOS 12.3 G13 ABI modeled in `kernel/modules/gpu/agx/fw`. The local recovery
volume contains two G17X IM4P containers. Each has a G17S (`a010`) and G17C
(`a000`) Mach-O; `extract_firmware.py` deterministically selects `a000`.

| Role | Bytes | Mach-O UUID | Virtual end |
|---|---:|---|---:|
| `armfw_g17x` | 1,579,528 | `0EDFE976-E37B-3E68-9D64-E3ABF7772D11` | `0xfffffc000017c000` |
| `armfw1_g17x` | 1,612,328 | `E324121D-8058-361E-9169-FCDE40123948` | `0xfffffc0000184000` |

Both images identify `RTKit-3255.120.11.release`, firmware generation G17,
build variant G17C A0, and SKSM support. Diagnostic strings explicitly reject
a host/firmware interface mismatch and distinguish host-mapped firmware
allocations. The primary virtual size (`0x17c000`) and the second role's extra
`0x8000` agree with sizes independently recovered from the firmware buddy.
The modern driver also contains AGFI scheduler/channel types absent from the
existing Vinix structures.

M5 Max exposes two independent `iop,ascwrap-v6` DeviceTree nodes and RTBuddy
services: `gfx-asc` has role `GFX`, while `gfx1-asc` has role `GFX1`. Each has
its own `0x88000` register aperture, mailbox at aperture `+0x8000`, firmware
image, and four interrupts. The live inspection manifest now records both as
`asc_roles`, and native T6050 discovery fails closed unless both translated
ASC apertures are present. The existing `asc` manifest key remains an alias
for the primary role so older captures remain readable.

The host boot path preserves that split all the way through the AKF transport.
`AGXArmFirmware::bootFirmware` clears the two role-started bytes, invokes the
transport boot method separately with root mappings at host members `0x19f8`
and `0x1a30`, requires both calls to succeed, and then waits for its shared
ready flag. `notifyFirmwareStarted(role)` selects a role record from
`host+0x19d8 + role*0x38` and sends `0x81 << 48` with that role's root IOVA
inserted into bits `43:0`. Incoming message type is bits `53:48`: type `2`
dispatches the firmware callback, while type `9` consumes a one-shot guard at
host member `0x1a48` and sends `0x89 << 48` through both role transports. The
recovery tool now pins every one of those instruction sites; a generic reply
on one mailbox is therefore not a valid G17 initialization acknowledgment.
Vinix now mirrors this topology in its inactive G17 boot path: role 1 has a
separately mapped ASC aperture and RTKit mailbox, both transports must boot,
each receives its own root message, and type 9 broadcasts the recovered reply
to both. The path does not allocate the legacy G13 channels or accept an
arbitrary packet as an INIT acknowledgment. The whole-chip launch gate is
still closed, so these routines cannot yet start either M5 Max ASC.

The separately version-pinned `AGXFirmwareKextG17XRTBuddy` binary confirms the
raw endpoint binding beneath that host interface. Its endpoint matcher accepts
service IDs `0x20` and `0x21`, stores distinct endpoint objects, enables both,
and uses only the `0x20` object for `readMessageFromAKF` and
`sendMessageToFirmwareGated`. Endpoint `0x21` is the doorbell service. The
receive trampoline forwards both the 64-bit message and the RTBuddy object's
firmware-role field to `AGXArmFirmware::receivedMessageFromAKF`. These anchors
validate Vinix's endpoint selection but do not establish the still-missing
work-command or completion-ring formats.

Disassembly of the primary image's endpoint-`0x20` bootstrap handler provides
the first byte-accurate root anchors:

- the init message matches `(message & 0x00bf000000000000) ==
  0x0081000000000000`, with the root IOVA in the low 44 bits;
- the first root word must equal `0x0c8bc322072804c0` or firmware aborts with
  the host-interface mismatch diagnostic;
- firmware copies the first `0xc8` bytes, then requires the 32-bit field at
  offset `0x2c` to be nonzero for host-mapped allocations.

The symbolized local `AGXArmFirmware::initFirmwareData` routine independently
confirms the complete top-level pointer placement. It constructs separate
roots for firmware roles 0 and 1, writes the role at `0x28`, and writes `1` at
`0x2c`. The corresponding firmware handler copies and consumes these fields:

Each root occupies its own 16 KiB host allocation, rounded to and aligned on
the M5's 16 KiB kernel page. Role 0 keeps its CPU/GPU mapping objects at host
members `0x19e0`/`0x19e8`; role 1 uses `0x1a18`/`0x1a20`. The CPU address is
obtained through mapping vtable offset `0x138` while building the headers, and
both firmware-GPU mappings are explicitly prepared before boot and completed
afterward. `fw.G17BootstrapPage` and `initialize_g17_bootstrap_page` now model
and deterministically clear the complete allocation rather than copying an
unbacked `0xc8` header.

| Root offset | Host allocation | Observed role |
|---:|---:|---:|
| `0x08` | bootstrap region from host member `0x1a58` | both |
| `0x18` | firmware shared data (`0x4c0` bytes; GPU members `0xab8` / `0xbe8`) | role 0 / 1 |
| `0x20` | runtime data (`0x1ca0` bytes; GPU member `0x388`) | both |
| `0x30..0x97` | platform configuration block | both |
| `0xa8` | small shared data (`0x20` bytes; GPU members `0xad0` / `0xc00`) | role 0 / 1 |
| `0xb0` | primary region (`0xe440` bytes; GPU member `0xce0`) | role 0 |
| `0xb8` | secondary region (`0x6f0` bytes; GPU member `0xce8`) | role 1 |
| `0xc0` | secondary auxiliary region (`0xa8` bytes; GPU member `0x398`) | role 1 |

The two small shared records at root offset `0xa8` have a complete 32-byte
layout. Their host-owned words are ktrace state at `0x00`, host-ready `1` at
`0x04`, and the system-sleep notification at `0x08`. Firmware publishes its
power state at `0x10` and monotonically observed ASC power generation at
`0x1c`; host wait/snapshot routines consume those exact words for both roles.
Offsets `0x0c`, `0x14`, and `0x18` remain reserved. Vinix now constructs the
host-owned initial state and leaves the firmware-owned/reserved words zero.

The single runtime allocation at root offset `0x20` is shared by both roles.
Its `0x1ca0`-byte size is not sufficient to construct it: four symbolized
initializers populate it from host policy and platform state. The recovered
producer establishes these larger regions:

| Runtime range | Bytes | Producer source |
|---:|---:|---|
| `0x054..0x059` | `0x6` | accelerator halfwords at `0x768..0x76d` |
| `0x0a4..0x0e3` | `0x40` | firmware host object at `0x27c8` |
| `0x0ec..0x7c3` | `0x6d8` | complete power-controller snapshot |
| `0x7c4..0x7eb` | `0x28` | Smart Idle policy at `0xe948..0xe96f` |

The power-controller snapshot is rearranged rather than copied linearly. Two
64-qword tables from source offsets `0` and `0x248` land at runtime offsets
`0x26c` and `0x4b4`; the surrounding scalar copies cover the rest of the
destination range without holes. On the pinned G17C driver, accelerator
vtable slot `0xd80` resolves to
`AGXAccelerator::populateDPEPPTConfigData`. That complete implementation
clears `0x6e0` bytes at source offset `0x5c`; the snapshot reads only source
offsets `0x60..0x737`. Runtime `0x0ec..0x7c3` is therefore proven to start
entirely zero, and Vinix now initializes that exact range explicitly.

The earlier 64-byte performance-controller slot has a separate lifetime.
`AGXArmFirmware::setupConfig` explicitly clears all 57 meaningful source bytes
at host-object offsets `0x27c8..0x2800`; the seven remaining copied bytes are
alignment padding. The runtime snapshot therefore begins with no controller
or boost override active. Vinix reproduces those zero values and clears the
reserved tail deterministically. This does not discard the M5 Max boost
policy: the firmware getters fall back to the accelerator's DeviceTree-backed
minimum-utilization and CE-step values while the runtime override-valid fields
remain unset.

The G17 accelerator vtable also selects the checked PI_300 `configureDevice`
and `configurePowerAndPerformanceController` override chain. The former
installs platform halfwords `ffff, 0028, ffff`. The latter replaces the base
Smart Idle delay with `1500` microseconds and the minimum-confidence value
with IEEE-754 `0.6`; the remaining recovered values are `1.0, 0.8, 0.2, 0.9,
0.1, 0.25, 0.9`, followed by a reset count converted by the firmware from
integer `6` to float `6.0`. Vinix writes the resulting 40 runtime bytes
directly. The source is accelerator offset `0xe948`, not `0xf948`; the ARM
initializer forms an `accelerator+0xe000` base before its `0x948` loads.

The same recovery verifies deterministic startup words throughout the
object. In particular, `0xa04..0xa2b` is cleared; the callback result at
`0x1c2c` and the normalized role count at `0x1c41` are dynamic;
`0x1c45..0x1c50` is cleared; and the four unaligned RIART words at `0x1c81`,
`0x1c85`, `0x1c89`, and `0x1c8d` start as `1, 0, 0, 0`. Short symbolized
accessors independently fix the register-override table at `0x804` (16
records of `0x18` bytes, count at `0x984`), progress/timeout controls at
`0x99c..0x9dc`, four six-byte firmware-utilization records at `0x9eb`, and
keepalive controls at `0x1c30..0x1c3f`.

The role-0 firmware immediately dereferences the allocation at `0x18`; its
first word leads to the large hardware/configuration payload. These names are
allocation-level descriptions only: none imply compatibility with the older
G13 nested structures.

The platform block is an exact `0x68`-byte copy from the object reached
through host member `0x298` and pointer offset `0x1a948`. It is copied into
both roots without role-specific changes. The pointer is the G17 legacy
shared-GART backing object, whose vtable slot `0x178` resolves to the cloned
PI-300 `initGartInfo` implementation. That producer initializes every byte in
the copied range at object offsets `0x18..0x7f`: the recovery tool verifies
its scalar literals, three identical 16-byte range descriptors, 16 KiB page
parameters, and fixed address-range values. `fw.G17PlatformConfig` now
constructs that exact byte sequence. Individual field semantics remain
conservatively unnamed, and root bytes `0x98..0xa7` remain opaque.

The object at root offset `0x08` is now independently recoverable. The host
allocates a 4 KiB requested payload rounded to the G17 firmware's 16 KiB page,
keeps its CPU mapping at member `0x1a50` and GPU mapping at `0x1a58`, and
publishes the firmware-converted GPU address to both roots. Its preparation
cursor is a 32-bit byte offset at host member `0x1ac0`.

The buffer is a sequence of `0x18`-byte register records:

| Offset | Bytes | Meaning |
|---:|---:|---|
| `0x00` | 8 | value or physical address |
| `0x08` | 4 | register |
| `0x0c` | 4 | auxiliary value |
| `0x10` | 4 | record kind |
| `0x14` | 4 | untouched padding |

Kinds `1`, `2`, and `3` encode 32-bit writes, 64-bit writes, and 64-bit
physical-address writes. Kind `0` terminates the sequence. Before boot, the
driver resets the cursor, invokes accelerator vtable slot `0xa88`, then
appends a terminator whose first `0x14` bytes are zero. In the pinned G17X
vtable that slot resolves through its authenticated kernel rebase to
`AGXAccelerator::populateInitSequenceFirmware(unsigned char).8148`; the
entire implementation is `bti c; ret`. T6050 therefore contributes no
register writes, and the safe Vinix representation of this region is a
zero-initialized 16 KiB mapping beginning with the kind-zero terminator.

The driver's allocation descriptors independently establish the exact sizes
of every object published directly through a root. The `0x4c0` shared object
contains host-written addresses at `0x00`, `0x08`, `0x10`, and `0x200`, a
five-address cluster beginning at the deliberately unaligned offset `0x254`,
additional addresses from `0x2d0` through `0x2f0`, a state byte at `0x3e0`,
a `0x90`-byte status area at `0x3e1`, a role-1-only address at `0x471`, and a
16-byte calibration value at `0x479`. G17-only packed structures now preserve
those offsets and keep all unknown ranges opaque.

Within each shared object, offsets `0x1a0`, `0x1a8`, `0x1b0`, and `0x1b8`
publish the role-local device-control ring's read-index, CFI-index,
write-index, and entry GPU addresses. Eight additional GPU addresses occupy
`0x1c0..0x1f8`; their allocation bindings are recovered, but their firmware
semantics remain unnamed. The exact direct publications recovered from
`AGXArmFirmware::initFirmwareSharedData` are:

| Shared offset | Role 0 GPU member / bytes | Role 1 GPU member / bytes |
|---:|---:|---:|
| `0x000` | `0x300` / `0x2710` | `0x300` / `0x2710` |
| `0x008` | `0x338` / absent (`0` bytes) | `0x338` / absent (`0` bytes) |
| `0x010` | `0x340` / `0x88` | `0x340` / `0x88` |
| `0x200` | `0xac0` / `0x79800` | `0xbf0` / `0x79800` |
| `0x254` | `0x308` / `0xc18` | - |
| `0x25c` | `0x310` / `0x1048` | - |
| `0x264` | `0x318` / `0xe10` | - |
| `0x26c` | `0x328` / `0x68` | - |
| `0x274` | `0x330` / `0x800` | - |
| `0x471` | - | `0x320` / `0x11dd0` |

The `0x338` output belongs to the firmware BRN-workaround-table allocation
descriptor (`0x2f0` CPU / `0x338` GPU). Its size comes from accelerator vtable
slot `0xf90`, which resolves on G17X to
`getSizeOfFWBRNTable().8051`. That implementation returns zero. The G17
firmware vtable's address converter at slot `0x2d8` is also an identity
function, so both shared objects intentionally contain zero at `0x008`; no
BRN table is allocated or populated on T6050. Role 0 may additionally publish
an address at `0x2d0` when the platform flag at `0xf754` is set; its source is
the pointer at platform offset `0x13768`.

Four further optional service addresses are produced from platform pointers
at `0x11560` and `0x11568` and written to role 0 offsets `0x2d8`, `0x2e0`,
`0x2e8`, and `0x2f0`. Role 1 mirrors the role-0 values at `0x2d8` and
`0x2e8`; both roles explicitly clear `0x2f8`. Each service pointer is
nullable in the pinned producer. A missing outer service clears the first
address of its pair, while a missing nested object at member `0x58` produces
a zero second address. The non-null mapping objects expose their GPU address
through vtable slot `0x158`. Vinix may therefore leave all four service
addresses zero when it does not instantiate those optional services.
Platform scalars at `0xf7c0`
and `0xf834` populate role 1 offset `0x300` and role 0 offset `0x304`,
respectively. Both roles copy the same 16-byte platform calibration block
from `0xf790` to the deliberately unaligned offset `0x479`. Finally, role 0
sets its byte at `0x3e0` to `0xff` and clears the following `0x90`-byte status
area. The G17 vtable's selected `halGetDefaultUscMaxTgmem` implementation
returns 12, which `configureDevice` stores at `0xf7c0`. The `0xf834` GVDM-mode
field retains its zero/default sentinel during bootstrap; its only direct
writer is `setGVDMMode`, called later by two performance-counter access paths.
The same base configure path explicitly clears all 16 calibration bytes at
`0xf790`, and the PI_300/G17 override chain does not replace them. Vinix now
publishes values 12 and 0 to the two role-specific scalar fields and leaves
both calibration copies zero. The optional service objects' semantic names
remain unknown.

The auxiliary publications at `0x1c0..0x1f8`, in order, come from GPU members
`0xb40`, `0xb60`, `0xb48`, `0xb68`, `0xb50`, `0xb70`, `0xb58`, and `0xb78`
for role 0. Role 1 uses `0xc70`, `0xc90`, `0xc78`, `0xc98`, `0xc80`, `0xca0`,
`0xc88`, and `0xca8`. Their corresponding sizes are `0x30`, `0x4800`,
`0x1b0`, `0x28800`, `0x30`, `0x9000`, `0x30`, and `0x4800` bytes.

Vinix now has a separate G17 ownership graph which allocates all of these
objects with 16 KiB alignment, maps them through the native UAT, publishes
the accelerator and auxiliary addresses in their role-specific shared
objects, initializes the recovered role-0 sentinels, and builds both root
pages. The shared platform values and runtime DPE/PPT policy are now complete.
The graph deliberately reports itself unbootable after construction because
hardware-configuration scalar/derived tables, firmware channel construction,
and work-command producers remain incomplete. This fail-closed path prevents
the older G13 channel or InitData layouts from reaching `MSG_INIT` on T6050.

Three nonzero allocations have fully recovered initial contents even though
their later field semantics remain unnamed. `AGXFirmware::initFirmwareData`
clears every byte of the role-0 `0x68`-byte allocation published at `0x26c`,
the role-0 `0x800`-byte allocation published at `0x274`, and the `0x88`-byte
shared-control allocation published at `0x010` in both roles. Dedicated G17
types and zero constructors represent these objects without borrowing an
older firmware generation's layout.

The other three role-0 bootstrap allocations are also initialized without
platform-dependent data. The `0xc18`-byte object at shared offset `0x254` and
the `0xe10`-byte object at `0x264` remain fully zero. The `0x1048`-byte object
at `0x25c` is cleared and then receives `0xffffffff` sentinels at offsets
`0xa18` and `0xa30`. Together with the zero regions at `0x26c` and `0x274`,
this establishes the complete initial contents of the five-address role-0
cluster.

`fw.G17BootstrapHeader` records the verified top-level fields and treats the
platform block as an explicit typed input. `fw.initialize_g17_bootstrap_region`
constructs the now-verified root-offset-`0x08` target.
`fw.G17FirmwareSharedBindings` likewise requires all recovered mandatory
publications before constructing either role's shared object. The remaining
bytes and nested allocation contents stay opaque, and `can_boot_firmware()`
remains false for G17.

### Firmware callback events

The callback validator accepts event types `0`, `1`, `4`, `6` through `15`,
plus type `29`. The generated recovery now reports every `0..15` jump-table
target and the exact internal record/enum identity for every typed arm, so
action accounting is explicit.
Types `2`, `3`, `5`, and `11` have slots that jump straight back to the drain
loop, but the validator rejects `2`, `3`, and `5`; accepted type `29` takes
the same path before jump-table dispatch. Type `0` is a different case: it
calls firmware vtable slot `0x878`, which the selected
`AGXArmFirmwareASC` class resolves to
`AGXArmFirmware::handleFirmwareControllerEvent`; that implementation is
exactly `bti c; ret`. Vinix therefore has two accepted direct host no-ops and
one vtable-resolved no-op, three effective no-op types in total. The recovery
reports the three validator-rejected reserved slots separately.

Type `4` is `AGFIFirmwareEventHWRecovery` / `GPURestart`. Apple validates its
signed stamp slot at event offset `+0x0c`, passes the body through firmware
vtable slot `0x1d0`, and calls `IOGPUScheduler::signalHardwareError` with
restart request 1. Vinix validates the recovered record and transitions the
GPU to its fail-closed error state. Continuing would be unsafe until Vinix has
the corresponding hardware reset and command replay engine.

Type `7` is `AGFIChannelErrorEventArgs`. Its fixed header holds a subtype below
5 at `+0x04`, a data-master type below 3 at `+0x08`, and the same signed stamp
slot convention at `+0x0c`. Apple's much larger handler finds the owning
channel and performs subtype-specific recovery. Vinix validates the fixed
header and conservatively stops the whole GPU until that channel lifecycle is
available.

Type `8` is `AGFIFirmwareEventMetrologyAging`: it reads a 32-bit result from
event offset `+0x04` and sends message type 2 only to the optional
`function-reliability_monitor` platform service retained at firmware
`+0xfb0`. Apple itself returns to the drain loop if the service is absent, so
Vinix's no-service path validates and consumes the event. Type `14` is
`AGFIFirmwareEventRTCompletionInfo`; it reads one unaligned 64-bit value from
event offset `+0x04` and calls
`IOGPUFenceMachine::notifyCLPCIOPerfControl`. IOGPU only fans this value out to
optional CLPC performance observers; it does not update a command stamp or
fence. Vinix has no CLPC policy/observer layer, so it validates and consumes
this advisory event.

Type `10` is `AGFIFirmwareEventSharedEventSignalComplete`. Apple requires its
unaligned 64-bit ID at `+0x04` to be nonzero, optionally release-stores byte 1
when the word at `+0x14` is nonzero, then narrows the ID through
`IOSurfaceRoot::signalEventID(unsigned int)`. That target signals only an
already registered `IOSurfaceSharedEvent`; a missing ID is a no-op. Vinix has
neither an IOSurface registry nor a producer for Apple's shared-event command,
because its userspace ABI synchronizes through DRM syncobjs. It therefore
validates and consumes the record as the equivalent empty-registry path. The
extractor now includes `com.apple.iokit.IOSurface`, allowing the recovery to
pin the cross-kext call by symbol rather than by its build-specific address.

Type `12` is `AGFIFirmwareEventProcessExitComplete`. Its unaligned 64-bit ID
at `+0x04` indexes an `IOGPUWeakNamespace`: Apple calls `getObject`, removes
the ID, and returns immediately when the lookup did not find an object. Vinix
does not construct Apple's host-side IOGPU object namespace, so every lookup
is necessarily that empty-namespace case. The callback validates and consumes
the record; adding a native equivalent registry later will require porting the
object-specific teardown path as well.

Type `6` is `AGFIFirmwareEventPMRequestMemory`. Its fixed record contains a
signed stamp slot at `+0x04` (`-1` or one of 128 slots), a parameter-manager
index below `0x7f` at `+0x08`, a request value at `+0x0c`, a request kind below
`0x40` at `+0x10`, and an unaligned firmware token at `+0x14`. The interrupt
handler copies those fields into an eight-entry, `0x20`-byte private host ring
and wakes `AGXAccelerator::allocateMemoryEvent`; allocation is intentionally
deferred out of interrupt context.

That worker resolves the indexed object as an `AGXHWParamBufferManager`, takes
its parameter-management member at `+0x98`, and invokes vtable slot `0x190`.
Both the physical and virtual implementations resolve that slot to
`growImmediately()`. Only after the grow call does Apple build this `0x40`-byte
device-control response:

| Offset | Field |
|---:|---|
| `0x00` | command type `8` |
| `0x04` | request kind |
| `0x08` | manager index |
| `0x0c` | signed stamp slot |
| `0x10` | request value |
| `0x14` | request kind, repeated by the host-record copy |
| `0x18` | firmware token |
| `0x20` | `0x20` zero bytes |

Submission flags are `0x19`; command type 8 selects role 0, verifies the token
against accelerator member `+0x688`, publishes the complete response entry,
and sends one synchronous `0x8400000000000011` notification. The recovery
tool now verifies the interrupt copy, worker registration, manager class,
physical and virtual grow targets, response construction, role table, token
check, and doorbell. Vinix has matching typed validation, response encoding,
and serialized ring staging, but still fails closed on type 6: acknowledging
before an equivalent parameter-buffer allocator exists would tell firmware
that nonexistent backing memory is ready.

Types `13` and `15` operate a second memory subsystem,
`AGXUSCPrivMemFList`. Type 13 (`AGFIFirmwareEventUMAGrowPool`) carries a
signed stamp slot at `+0x04`, an FList index below 256 at `+0x08`, required
nonzero unaligned values at `+0x0c` and `+0x14`, then a 64-bit result at
`+0x1c` and 32-bit flags at `+0x24`. Apple resolves the indexed FList and
calls vtable slot `0x180` on its grow engine at `+0x50`; the selected G17
implementation is `IAGXUSCPrivMemGrowEngine::retireGrowRequest(...)`.

Type 15 (`AGFIFirmwareEventUMAThresholdInterrupt`) carries an FList index below
256 at `+0x04`. Apple compares the FList's current and requested thresholds at
`+0x80` and `+0xe8`; when growth is required it publishes the new value and
calls accelerator vtable slot `0x1120`, which resolves to
`halUpdateUMADesc(...)`. It then zeroes a complete `0x40`-byte device-control
entry, writes command `0x21` and the FList index at offsets `0` and `4`, and
submits it through the device-control path. Vinix validates both event records
and can encode/stage command `0x21`, but intentionally does neither host action
and sends no acknowledgement until its USC-private-memory manager exists.

Type `9` is `AGFIFirmwareEventUMARequestMemory` /
`kAGFIFirmwareEventTypeUMAAsyncAlloc`. Apple first checks a disable byte at
accelerator `+0x1a960`, then validates a request index below 256 at event
`+0x04`, a nonzero unaligned 64-bit value at `+0x0c`, and a signed stamp slot
at `+0x14` (`-1` or below the dynamic stamp count). Event word `+0x08` is not
copied. The remaining fields are placed in a private 64-entry, `0x20`-byte
host ring whose control and entry arrays are at accelerator `+0x1a2f0` and
`+0x1a9af0`:

| Host offset | Source |
|---:|---:|
| `0x00` | event `+0x04` |
| `0x04` | zero |
| `0x08` | event `+0x0c` (8 bytes) |
| `0x10` | event `+0x14` (8 bytes) |
| `0x18` | event `+0x1c` |
| `0x1c` | zero |

When the ring is full, a zero event word at `+0x1c` drops the private host
request; a nonzero word polls for space in 100-microsecond intervals. A queued
request signals the event source at accelerator `+0x470`. Crucially,
`AGXAccelerator::start` binds that source to
`AGXAccelerator::allocateUMAMemoryEvent`, and the complete implementation in
the UUID-pinned G17 driver is exactly two instructions, `bti c; ret`. It never
drains the private ring, allocates memory, or sends a device-control response.
The recovery tool asserts the typed validation, both full-ring branches, copy
map, worker registration, and exact no-op body. Vinix validates and consumes
type 9 directly, omitting a host-only queue whose selected consumer has no
effect.

Type `1` remains the 128-stamp completion event. Types `6`, `13`, and `15` are
now the only accepted callback records with deliberately unimplemented host
actions: their wire/action contracts are recovered, but Vinix still lacks the
parameter-buffer and USC-private-memory services they require, so those three
paths remain fail-closed.

### Command rings

The local G17 driver no longer submits the legacy G13 work messages currently
modeled by Vinix. Its named `AGXAcceleratorRing` accessors establish a common
`0x30`-byte shared state with 256-entry indices at these offsets:

| Offset | Field |
|---:|---|
| `0x00` | read index |
| `0x10` | CFI/completion index |
| `0x20` | write index |

`AGXArmFirmware::encodeAcceleratorRingCommand` and the ring enqueue routines
also establish a `0x18`-byte data-master entry and a `0x40`-byte device-control
entry. The complete data-master encoder preserves the reserved qword at
`0x00`, then writes the channel data address at `0x08`, command type at `0x10`,
submission index at `0x14`, channel ID at `0x16`, and flags at `0x17`. The
address and ID come from channel `+0x80` and `+0x18`; the flags byte is
`1 & ~channel[0x3c]`. Vinix zeroes the complete entry before every encode so
the preserved qword stays deterministic even after ring wrap.

The TA, 3D, and CL producers pass command types 0, 1, and 2. Each engine owns
four rings, selected by the channel priority. Their host objects begin at
`0x3b0`, `0x450`, and `0x4f0`, use a `0x28` stride, and own exact
`0x30`/`0x1800`-byte state and entry allocations. `initFirmwareData`
publishes their twelve address records into the first `0x180` bytes of the
primary role's `0x79800`-byte large region: each priority is one `0x60`-byte
record containing TA, 3D, and CL `0x20`-byte subrecords.

`nextEntry` is serialized by an `IOCommandGate`, treats
`((write_index + 1) & 0xff) == read_index` as full, and therefore exposes 255
slots. After encoding, all three execute `dmb ish` and publish the wrapped
write index. `fw.enqueue_g17_data_master_entry` reproduces this with a release
store, while the retained firmware graph provides one host lock per ring.
After publication, each ARM submit wrapper sends
`(0x83 << 48) | (priority << 2) | command_type` through the primary role
transport at host member `0x19d8`. Vinix recovers this routing and stages it
behind the existing firmware boot and command-encoder gates.

The two other host-side ring objects at `0xad8` and `0xc08` are role-local
device-control rings, not data-master rings. Each is five qwords: its dispatch
table followed by CPU and GPU addresses for the `0x30`-byte state allocation,
then CPU and GPU addresses for a `0x4000`-byte entry allocation containing
256 `0x40`-byte entries. The recovery tool validates both allocation pairs
and all four firmware-visible addresses published in the corresponding shared
object.

Each later work context has a second level of channel state. The base
`AGXChannel::resetChannelState` implementation proves a `0xc0`-byte state
object, a `0x70`-byte uncached control header, and an 8-byte cached command
pointer stride. Host channel members `0x58`/`0x60`/`0x68` hold the CPU
addresses for state, uncached control, and cached commands; members
`0x80`/`0x88`/`0x90` hold their corresponding GPU addresses. The outer data
master entry publishes the state GPU address from member `0x80`.

The state object starts with uncached and cached GPU addresses at `0x00` and
`0x08`. Its checked reset fields include a context cookie at `0x10`, mode 4
at `0x28`, `0xffffffff` sentinels at `0x24` and `0x44`, a platform value at
`0x48`, and an unaligned platform address at `0x9c`. The uncached header keeps
its read and write indices at `0x00` and `0x40`, a `0xffffffff` sentinel at
`0x50`, and the ring-entry count at `0x60`.

Mode 4 at `0x28` is only the reset sentinel. `AGXChannel::getPriority` returns
that field, and `AGXArmFirmware::setChannelPriority` replaces the complete
`0x28..0x43` policy block before submission. The canonical Apple context
priorities `0`, `4`, `1`, and `2` select firmware/data-master priorities
`0`, `1`, `2`, and `3`, matching Asahi's realtime/high/medium/low UAPI order.
Vinix now applies the corresponding six-field profiles, including the
threshold, default subpriority 2, and QoS word, when it creates every native
G17 channel.

The firmware resource pools live at host firmware members `0x11c8` (state),
`0x1348` (uncached), and `0x1408` (cached). The latter two use the recovered
element-size formula `0x70 + configured_queues * 0x80`, with distinct cache
attributes. `fw.initialize_g17_channel` now constructs the checked portion of
all three mappings. Those two inputs are no longer unnamed:
`resetChannelState` only copies them out of its own object, but
`AGXChannel::init` seeds channel members `0x4c` and `0xf8` from the owning
`AGXCommandQueue` at `+0x498` and `+0x8b8`, so state `0x48`/`0x9c` are queue
properties rather than platform constants, and the ring-entry count at channel
`+0x54` is `min(requested, 0x80) * 16`. The runtime object also carries a
`0x4c`/`0x50` kick-channel QoS pair written by
`AGXArmFirmware::setKickChannelQos` through firmware member `0x380`; the shared
`0x4c` offset is a coincidence and the recovery tool checks both so they cannot
be confused.

The concrete channel wrappers also pin the `_AGFIDataMasterType` values instead
of inferring them from class names: `AGXTAChannel::init` passes 0,
`AGX3DChannel::init` passes 1, and `AGXCLChannel::init` passes 2 as the seventh
argument to `AGXChannel::init`. The extractor requires the `mov w6, #type` and
direct base-initializer call to remain adjacent in each wrapper.

Every one of those work channels has firmware channel ID `0x80`.
`AGXChannel::init` passes that constant and the accelerator from command-queue
member `0x538` to the imported `IOGPUChannel::init`; the independently
symbolized IOGPUFamily implementation stores the owner at channel `+0x10` and
the ID at `+0x18`. The outer data-master encoder narrows the latter to the byte
at entry `+0x16`. Vinix's G17 command constructor now supplies the recovered
ID and the initializer's zero channel flag rather than exposing either as a
submission input.

The ring request and context cookie are now pinned end to end as well. The
PI_300 device setup writes 80 at accelerator `+0x718`; an optional nonzero
override may live at `+0x11160`. `AGXCommandQueue::init` chooses the override
or fallback and stores it at queue `+0x880`. Both render and compute work-queue
allocators pass that word as argument 3, `IOGPUWorkQueue::init` retains it at
work queue `+0x54`, and `AGXChannel::init` derives
`min(request, 0x80) * 16`. T6050 therefore uses 1,280 cached command pointers,
or `0x2800` live bytes, inside each `0x2870`-byte cached pool element.

Every command queue also owns one 24-byte uncached `_AGFITimeStampQueue`
element from firmware stack `+0x1288`. The host timestamp object keeps its CPU
and GPU addresses at `+0x20` and `+0x28`; reset clears the shared element,
writes its own GPU address at element `+0x08`, and writes the update-mode flag
at `+0x10`. The object initializer clears its mode at host `+0x38`, so the
shared flag is initially zero until the one-shot mode setter changes it. The
render, lazy-TA, and compute channel allocation paths all load
that GPU address through command queue `+0x680` and pass it as channel
initializer argument 5. This proves that channel-state `+0x10` is the shared
timestamp-state GPU address, not a queue ID or opaque host pointer. Vinix now
has typed helpers for the timestamp state, ring capacity, and pool size.

Vinix now owns the corresponding per-DRM-queue allocation graph as well. A
render-capable queue receives TA and 3D channels, a blit-capable queue receives
the 3D channel, and a compute-capable queue receives the CL channel. Each uses
the recovered cached state/pointer mappings, uncached control mapping, shared
timestamp cookie, scheduler-state address, process ID, and 1,280-entry ring.
Queue destruction, final file close, allocation failure, and GPU shutdown all
release these mappings in reverse order. Firmware publication remains gated
until callback and completion handling are implemented.

The `0x8b8` end of that pair is now fully resolved.
`AGXCommandQueue::allocateSchedulerState` takes one element out of the
`AGFICmdQueueSchedState` firmware pool and publishes four members of the queue:
the element CPU address at `+0x8a0`, its owning resource at `+0x8a8`, its
allocation index at `+0x8b0`, and its GPU address at `+0x8b8`. The pool is bound
in `AGXArmFirmware::allocFirmwareData` against the resource stack at ASC
`+0x14c8`, with an element size of `0x40`, alignment shift 9, caching option 1
and no owning task; the stack derives `block_bytes = (page_bytes + 2 *
element_bytes - 1) & -page_bytes` and `elements_per_block = block_bytes /
element_bytes`. So channel state `+0x9c` is the GPU address of the queue's
`_AGFISchedulerState`.

The element's initial content is fixed too: Apple zeroes the first `0x38`
bytes, then writes `0xffff` at `+0x00`, `1` at `+0x05`, `0` at `+0x22`, `0xff`
at `+0x33`, and one byte copied from queue member `0x490` at its `+0x120`.
Vinix reproduces all of that in `fw.initialize_g17_scheduler_state`, taking
both of its client-supplied inputs as arguments.

Those two inputs are the last of the channel/scheduler unknowns and both now
resolve to values Vinix can produce for its own clients. `AGXCommandQueue`
never writes `+0x490` or `+0x498`: it inherits them from
`IOGPUCommandQueue::init`, which stores the owning `IOGPUDevice` at `+0x490`
and copies that device's `+0x60` to `+0x498`. `IOGPUDevice::init` sets `+0x60`
to `proc_pid(get_bsdtask_info(task))`, so **channel state `+0x48` is the
creating process ID**. The device is an `AGXShared`, whose byte `+0x120` is the
app GPU role: `AGXShared::init` defaults it to `2` and
`AGXShared::set_app_gpu_role` rejects anything `>= 4`, so **scheduler state
`+0x26` is the app GPU role, default 2, range 0..3**. Resolving these required
adding `com.apple.iokit.IOGPUFamily` to the local extraction set.

`initialize_g17_channel` and `initialize_g17_scheduler_state` now take
`owning_process_id` and `app_gpu_role` rather than opaque words, and the role
is range-checked the same way Apple's setter checks it.

### Second performance-state block

The `0x868` bytes after the AFR block were carried as opaque, but they are not.
Gated on accelerator byte `+0x505`, `initPowerAndPerformanceData` zeroes `0x848`
bytes at `+0x1cd8` and refills them with the same shape as the primary block at
`+0xfc4`: the maximum state index at `0x1cd8`, one Hz-to-MHz frequency per
state at `0x1cdc`, and two 16-column voltage matrices at `0x1d1c` and `0x211c`.
Its sources are the accelerator's SRAM-side arrays — state count at `0x1bb58`,
column count at `0x1bb5c`, frequencies at `0x1bb60` and voltages at `0x1bba0` —
rather than the primary arrays, and the same reciprocal conversion is applied.
The block occupies `0x844` of the `0x848` cleared bytes, which is the check
that the layout is right.

**On G17 the block is never filled.** Its producer is gated on accelerator byte
`+0x505`, and `getProbeScore` relays that byte from chip-info `+0x85` when it
copies the record's `0x80..0x8f` bytes to accelerator `+0x500`. That record is
cleared first and no selected G17C reader writes `+0x85` — the same fact the
fixed performance-state map fallback already rests on — so the producer's `TBZ`
always skips. An earlier pass here populated the block from the SRAM
performance-state data, which would have sent firmware a block Apple leaves
zero; Vinix now types the fields to record the layout and leaves them clear.

Finding this needed care about *which object* a store targets. Matching the
offset range alone attributes 95 writes to `AGX3DChannelSKSM::submitBuffer` and
43 to `AGXEventMachine`, none of which touch the hardware config. Following the
config pointer from firmware member `0x2b8` instead leaves two direct writes,
and reading around them exposes the loop that fills the rest.

### GPU identity registers and the chip variant

The chip-info fields behind the remaining late-control values are not opaque
accelerator state. `readChipInfo` builds the record from the GPU ID register
block at `0xd04000`, reading the version at `+0x00`, a count at `+0x08`, the
cluster configuration at `+0x10`, and three more identity words at `+0x14`,
`+0x18` and `+0x1c`. Vinix already knew the first three; all six are now named
in the `regs` module.

The version register also decides the chip variant. Byte 3 must be `0xb`, and
byte 2 selects: `2`, `3` and `4` map to variants `0x20`, `0x21` and `0x22`,
written to chip-info `+0x20` alongside a companion value of `0xa`, `0x14` or
`0x28` at `+0x74`.

The internal power dimensions come out of the cluster-configuration register
at `0xd04010` by plain integer arithmetic: `(cfg >> 16) & 0xf` is the power
group count at chip-info `+0x6c` / accelerator `+0x4ec`, `(cfg >> 8) & 0xff`
is columns per group, their product is the power column count at `+0x64` /
accelerator `+0x4e4`, `cfg & 0xff` lands at `+0x78`, and column count times
that lands at `+0x30`, reaching accelerator `+0x4b0`.

These dimensions are not the public `num_cores` and `num_mgpus` values in
`GPUConfigurationVariable`. The selected leakage producer indexes a static
eight-entry selector table with the `+0x4e4` count and copies `+0x4ec` values
into a two-element destination, which rules out the earlier interpretation of
those fields as this machine's public 40 cores and four GPU partitions.

That `+0x4b0` value is *not* what config `+0x2570` ends up using. The field has
two producers selected by accelerator byte `+0x506`, which is chip-info `+0x86`,
and `readChipInfo` reassigns `w22` to `1` well before storing it there with no
branch able to skip the assignment. The bit is therefore always set, the
scaled-core-count producer never runs, and the popcount producer wins. That
popcount reads the *second* mask pair: the first is the cleared head of the
chip-info record, so the select steps on by `0x10` to chip-info `+0x10`/`+0x18`,
a 64-bit and a 32-bit mask assembled from three words.

Those words are hardware. `readChipInfo` maps them separately from the ordinary
register accessor, but the base it uses is `getGPUPhysicalAddress()`, which
probe sets to `IOMemoryDescriptor::getPhysicalAddress()` of device-memory range
0 — the same SGX aperture `sgx_read32` already addresses. The masks are at SGX
offsets `0xe01500`, `0xe01504` and `0xe01508`, and `+0x2570` is their combined
population count. Vinix reads them and emits the field, counting from the
registers rather than from the published topology so a part with cores fused
off still comes out right.

The analyzer composes the chip-info relay with both matrix producers and checks
that these two fields are exactly their column-count inputs. Vinix decodes the
same register at run time and rejects dimensions beyond the recovered eight
column / two group capacities.

That variant is the same one the power model switches on. The `+0x480` relay
carries chip-info `+0x20` to accelerator `+0x4a0`, which is exactly the field
`populateMaximumPerformancePowerCS` compares against `0x21` when picking
`21.7`/`38600` over `12.29`/`24800`, and `calculateVddGpuLeakage` compares
against `0x22` when picking its leakage parameter table. The test suite
composes the relay delta with the chip-info offset and asserts it equals both
the accelerator member and the power model's recorded `chip_variant_offset`, so
those three recoveries cannot drift apart.

### Late-control block

`AGXArmFirmware::initFirmwareData` writes **36** distinct offsets in
`0x2540..0x270f`. An earlier pass here reported 27, because it matched stores
by their immediate offset and so missed every write that materializes its
offset into a register first (`mov w8, #0x2706; add x8, x9, x8; str wzr, [x8]`).
The write set is now derived by `config_pointer_stores`, which tracks the
config pointer from firmware member `0x2b8` and through `add`, and the fixed
and run-time sets are checked to account for all 36 between them.

Twenty-two are fixed for G17 and Vinix emits them: `1` at `0x2578`, `0x25a0`
and the 64-bit `0x26f0`, and zero at `0x2540`, `0x2548`, `0x255c`, `0x2560`
(128-bit), `0x2574`, `0x258c`, `0x259c`, `0x25a4`, `0x25a8`, `0x25b4`, `0x25b8`,
`0x25ec`, `0x25f0`, `0x2600` (64-bit), `0x26a8` (64-bit), `0x26c4`, `0x26e0`,
`0x2706` and `0x270a`.

`0x2560` is the one that needed the chip-info record to settle. It copies the
accelerator's core-mask pair at `+0x480`/`+0x488`, but only when either half is
nonzero. `getProbeScore` builds the chip-info record on its own stack at
`sp+0x10` and copies it to accelerator `+0x480` with a uniform `+0x480` delta,
so those halves are chip-info `+0x00` and `+0x08` — and neither selected G17C
reader writes them, so the guard never passes. The `stores_covering` helper
that proves this is now shared with the performance-state map fallback, which
rests on the same kind of never-written argument.

Five of those zeros come from the fixed feature mask `0x0001000018020000`
rather than from a literal: bits `0x07`, `0x25`, `0x26` and `0x35` land at
`0x25b4`, `0x259c`, `0x25a4` and `0x26c4`, and `0x2548` is
`((mask >> 4) & 4) | ((mask >> 6) & 2)`. All are clear, and the tool recomputes
them from the mask so a mask change fails loudly. Two more store through a
vector register, where the scan cannot see the value, so their producing
instructions are pinned directly.

`0x2570` and `0x2554` are emitted too. The first is the core-mask population
count described above. The second is a bit mask sized by a chip-info nibble
product: `readChipInfo` splits identity register `0xd04018` into six nibbles and
stores three pairwise products at chip-info `+0x48`, `+0x4c` and `+0x50`, each
pairing a low nibble with the one 16 bits above it, and the third reaches
accelerator `+0x4d0`. The producer turns that count into a mask, and since it
shifts in 64 bits and keeps the low word, any count of 32 or more yields all
ones, with a count past 63 saturated explicitly rather than wrapping on the
shift. Both are computed rather than constant, so the recovery tracks them
apart from the fixed values. Five more are fixed for a different reason: their accelerator sources are never
written. `0x2544`, `0x25f4`, `0x25f8`, `0x26a4` and `0x26bc` read accelerator
`+0x72c`, `+0x730`, `+0xf91c`, `+0xf914` and `+0xf958`, and a width-aware sweep
of the whole executable segment finds no store covering any of them, in either
the driver or the two firmware-buddy kexts. The accelerator is allocated
through the same zeroing typed operator new the ASC uses, at `0x1cbd0` bytes,
so those members keep zero and the fields they feed do too. `0x2544` is only
written at all when its source is nonzero, so it stays clear either way.

That sweep needs the width rules, and it needs reading. It flags a store at
`+0x728` inside `AGXAccelerator::idlePowerOffTimer` as covering `+0x72c`, but
that base is the accelerator plus `0x13000`, so the store lands at `+0x13728`.
A test pins both halves of that: the sweep really does flag it, and the base
really is offset.

Five more are settled by reading the producer rather than a source. `0x25bc`
and `0x25dc` are one 48-byte run of ones, written as a store pair plus a single
vector store, ending exactly at `0x25ec` — which the producer then sets to zero,
so the two do not overlap and the order does not matter. `0x26f8` and `0x26f9`
copy accelerator bytes `+0x6f0` and `+0x6f8`, which `configureDevice`
deliberately clears; the only other writers are fence-callback and
render-submission paths that run long after firmware data is built. `0x25ac`
would take a pair of ones, but its store is guarded by feature bit `0x26`,
which is clear in the fixed mask, so it never runs.

The last two are settled too. `0x26c0` takes a literal `1`, with nothing able
to reassign the register between the literal and the store. `0x269c` passes
firmware member `0x1ab8` through the address converter, and both ends are
known: the converter is `mov x0, x1; ret`, the identity already established for
the timestamp address, and a sweep finds exactly one store covering that
member — the constructor clearing it. So the field converts zero to zero.

Every one of the 36 fields is now accounted for: 34 fixed and two computed from
the core-mask and identity registers. That is what lets the boot gate's
late-control bit be cleared, leaving only the die-dependent power rows. With the `+0x480` delta established most
of those sources are now named as chip-info fields: `+0x4b0` is chip-info
`+0x30`, `+0x4d0` is `+0x50`, and the `0x2570` gate byte `+0x506` is `+0x86`.

### Channel command pools

Work commands are not allocated per submission: each type has a preallocated
slot ring described by a `0x40`-byte block in the firmware object, holding the
backing resource at `+0x08`, its CPU base at `+0x10`, a per-slot in-use byte
array at `+0x18`, the element size at `+0x20`, the slot count at `+0x28`, a
cursor at `+0x2c`, an exhausted flag at `+0x30` and a lock at `+0x38`.
`AGXFirmware::requestChannelCommandX` scans forward from the cursor for at most
`slot_count` entries, takes the first slot whose in-use byte is clear, and
returns `cpu_base + slot * element_bytes` while writing
`resource_gpu_address + slot * element_bytes` to the caller. It returns null
rather than blocking when the ring is full. `fw.acquire_g17_command_slot`
reproduces that scan exactly, including the cursor advance, under a per-pool
lock.

`AGX3DCommandDescriptor::complete` independently ties the main 3D command to
the pool block at `0x1688`: it takes the retained command CPU pointer from
descriptor `+0x438`, computes `(pointer - cpu_base) / element_bytes`, and
decrements the corresponding in-use byte under the same pool lock before
clearing the descriptor pointer. `fw.release_g17_command_address` reproduces
that reclamation with additional range and element-alignment checks.

Pool capacity is selected from the G17 accelerator member at `+0x11160`, with
the PI-300 fallback at `+0x718` set to `80` when that override is zero. The
four work pools use three times the selected capacity. Their shared
`PoolClass::createBacking` implementation rounds `element_bytes *
requested_slots` up to the 16 KiB kernel page size, then sets `slot_count` to
`backing_bytes / element_bytes`; consequently page padding can expose more
slots than the requested count. With the fallback request of 240 slots, the
work-pool geometry is:

| Command | Backing bytes | Actual slots |
|---|---:|---:|
| TA | `0x94000` | 242 |
| 3D | `0x204000` | 241 |
| FastBlit | `0x98000` | 243 |
| CL | `0xf4000` | 240 |

`fw.g17_command_pool_geometry` and `fw.initialize_g17_command_pool` reproduce
that page rounding and bind only exact-sized backing allocations, including a
zeroed host-only in-use byte for every actual slot.

### 3D command register lists

`generateRegisterListFor3D` runs four passes over the `0x2240`-byte 3D command
with a `0x720` stride. Each pass encodes a stream of GPU register writes at
pass base `+0xa0`, where every entry is 12 bytes: a selector word followed by
an *unaligned* 64-bit value. The selector word is not written wholesale — the
producer keeps the template bits already present under mask `0xfffc0006` and
ORs the selector into the rest. Alongside the stream the pass maintains the
stream's own GPU address at `+0x7a0`, derived from descriptor member `0x440`,
and two 16-bit counters at `+0x7a8` and `+0x7aa`, advanced by one and by 12
per entry.

The record framing is now settled. Pass `i` owns the stream bytes from
`i * 0x720 + 0xa0` up to its metadata at `i * 0x720 + 0x7a0`, so each pass has
exactly `0x700` stream bytes, and the next pass's stream begins at
`i * 0x720 + 0x7c0`, which is `0x14` bytes after the previous metadata ends.
There is no overlap; an earlier reading that compared the metadata offset
against the stride rather than against the next stream start was simply wrong.

The producer's exit block confirms the spacing independently: it copies each
pass's GPU address and entry count into a four-entry, `0x10`-byte summary array
in the descriptor at `+0x828`, walking the command with the same `0x720`
stride. `fw.append_g17_register_entry` now bounds itself against the recovered
`0x700` budget, and `fw.publish_g17_register_summaries` reproduces that copy.

### Register selectors

The exact HAL300 `encodeEntry` helper separates the first word into three
inputs. Bits 3..17 come from the 8-byte-aligned `w2` selector under mask
`0x3fff8`; bit 0 comes independently from `w3`; and bits 1, 2 and 18..31 are
preserved from the pool template under mask `0xfffc0006`. The unaligned 64-bit
`x4` value follows at `+4`. `fw.append_g17_register_entry` now implements that
four-argument contract and rejects non-aligned selectors or modes above one.

The producers form most selectors from constant bases in callee-saved
registers, followed by `ADD`, `SUB`, register `ORR`, or logical-immediate
`ORR`. A conservative backwards slice now resolves `w2` at every virtual
encoder call in the UUID-pinned driver:

| Producer | Literal selectors | Encoder calls | Mode 0 / 1 | Unique call selectors | Entry-emission sites |

| Producer | Constants | Descriptor loads | Expression trees | Still unsliced |
|---|---:|---:|---:|---:|

source. This includes 23 values traced through callee-saved copies to 19
dominating descriptor loads and four constants. The backwards slice rejects
ambiguous control-flow joins rather than choosing one path. A recursive slice
now reduces 105 more values to complete expression trees rooted in descriptor members,
constants, and known channel/command arguments. These include nested object
and paired loads, command-pointer spills through fixed stack slots, the old
destination of bitfield inserts, and the predicate plus both arms of ten
conditional selects. Six more values include both sides and the predicate of an
unambiguous single-branch forward merge. Three more preserve the tested bit,
both values and path orientation for a `TBZ` skip or one canonical two-arm
diamond. Four values combine the UUID-pinned
accelerator virtual methods at slots `0x10f8` and `0x1100`; their complete

Four more follow the typed resource chain used by
each producer through `IOGPUMemoryMap::getGPUVirtualAddress()`. The matching
base, legacy and secure vtable slot `0x158` entries and the accessor's exact
`ldr x0, [x0, #0x28]; ret` body are checked across both binaries before that
object load is admitted as an expression root. The exact three-compare
`8/4/2/default` initializer is represented as a four-way value node; its direct
3D use and the downstream 3D and FastBlit packers remain bounded, acyclic trees
under the depth-20 guard. Compare-zero branches preserve both sides of CL's
nullable-object selection. TA's nested test/compare gate records exactly when
bit `0x800` is added. The two remaining CL entries share a mode-selected low
bit and a table-or-fallback base. Their trees preserve the descriptor choices,
the static byte counter's post-increment, and the mode-2 `random() & 1`; the
direct call target is cross-checked against `_random` in the extracted kernel
image. That makes all 314 call-value formulas reproducible, and all 24
register-copy sites have complete trees. Loop back-edges do not
invalidate definitions that dominate from the function prologue, while forward
edges which can skip a register or stack definition remain rejected unless both
incoming values can be represented.
Each recovered `encoder_entries` record keeps selector, mode and
value provenance together in physical producer order.

Together with the normalized literal audit, this exposes 234 distinct static
selector values spanning `0x28` through `0x1ca78`. All ten inline record forms
are now located as well. Eight use mode 1 and static selectors: `{0x1738, 0x17e0}` in
3D, `{0x17e0, 0x17f0}` in TA and CL, and `{0x1738, 0x10008}` in FastBlit.
Their instruction anchors also distinguish the constant-one values from
FastBlit's computed control value. The raw move-immediate audit contains 59
encoded fields but normalizes to 58 selector values after removing mode bit 0.

CL has the remaining two adjacent inline records. Their selectors are
symbolic expressions based on `low32(accelerator_base + 0x13200)`, with
selector addends `0x8` and `0`, both in mode 1; their values come from masked
channel word `+0x1b8`. The first value is `(word & 0x7fffffffc00) | 5`; the
second adds `(accelerator[0x4b0] * 3) << 11` to that masked word. The recovery
tool pins both construction sequences rather than pretending their
runtime-dependent selectors are static constants.

The recovery still reports `selectors_complete: false` for the finite static
set because two selectors are necessarily runtime-computed. It separately
reports `selector_formulas_complete: true`: every virtual and inline selector
has a construction formula, and all ten inline value forms are complete. What
address space the selectors name is still unresolved — they are not the SGX
MMIO offsets in the `regs` module.

The possible ordering is no longer inferred from sorted call offsets. The
recovery tool walks every direct `B`, `B.cond`, `CBZ`/`CBNZ`, and `TBZ`/`TBNZ`
edge, treats authenticated-call `BRK` failures as traps, and collapses the full
instruction graph to the next externally visible record emissions. The result
contains 99 nodes/109 edges for 3D, 78/79 for FastBlit, 49/53 for CL, and
98/103 for TA. It preserves the 3D pass-loop back edge and distinguishes a
normal return before the first 3D record from trap-only paths. Thus
`machine_order_complete` is true: the graph says exactly which record can
follow which, independently of the predicate semantics attached next.

That predicate layer is now recovered too. Of the raw conditional branches,
280 are authenticated-pointer guards whose alternate arm only executes `BRK`;
they are kept as trap guards rather than misclassified as register-list
choices. Exactly 21 branches alter the next record or normal-return path: eight
in 3D, two in FastBlit, five in CL, and six in TA. Twenty slice directly to
descriptor/object expressions. The last is `CBNZ w23` in 3D's four-pass loop;
its initialization to zero, increment, limit comparison, and range 0..3 are
all pinned as a loop-induction predicate. Consequently both
`machine_order_complete` and `predicate_expressions_complete` are true.

Porting this now-complete declarative graph and its value expressions into the
kernel remains before a 3D command can be built. The register list is assembled
in firmware-only memory, so the IOKit tracer cannot observe it directly.

### Userspace command stream

The one part of the work-command path that *is* userspace-visible is the
command stream Mesa would have to emit.
`AGXHardwareKernelCommand::parseAndValidate` reads it through an
`AGXSharedStreamParser` holding `{start, end, cursor}` at `+0x00`, `+0x08` and
`+0x10`. Each record is a fixed `0xc0`-byte header, copied into the command
object at `+0x10`, followed by a payload whose length is the `u32` at record
offset `0x9c`. When the cursor reaches the end the parser writes the marker
`0x100` to command `+0x0c` instead of reading a payload.

Three optional blocks are selected by fields in that fixed header. Record
`+0x90` is the byte length following a primary extension's four-`u32` count
header; a nonzero value consumes that length plus the 16-byte header from the
primary parser. The first two counts describe consecutive 2-byte and 24-byte
arrays. The header is copied to command `+0xe8`, with array pointers at `+0xf8`
and `+0x100`.
The other two blocks are consumed from the separate auxiliary parser passed as
the method's second stream argument, so they must not be appended while walking
the primary segment:

| Gate | Auxiliary byte length | Count header | Arrays |
|---:|---:|---:|---|
| record `+0x88` | record `+0x8c` | four `u32`s -> command `+0x120` | four consecutive 2-byte arrays -> `+0x130`, `+0x138`, `+0x140`, `+0x148` |
| record `+0x94` | record `+0x98` | four `u32`s -> command `+0x150` | `(count0 + count1)` 8-byte elements -> `+0x160`, then `(count2 + count3)` -> `+0x168` |

A complete parse stores byte `1` at command `+0x08`. An invalid auxiliary
span or array writes `0x102` at `+0x0c`; the primary terminator/error path uses
`0x100`. The recovery pins the bounds arithmetic, all count loads, pointer
members, and both grouped-count additions rather than inferring this layout
from the capture.

That framing was cross-checked against real bytes rather than only asserted.
The captured clear/triangle pair from this Mac begins `{magic 0x10000, length}`
where the length field is exactly the 2752 bytes captured, and walking it with
the recovered record format yields one record of `0xc0 + 0x9d0` bytes followed
by a primary extension, identically for both phases. The extension has a
`0x10`-byte count header, zero 2-byte elements, and one 24-byte element, which
accounts for all 40 remaining bytes. `trace_diff.py --walk` performs that walk
with zero unexplained trailing bytes, so the check is reproducible rather than
a one-off, and it fails loudly if a payload or extension would run past the
segment. It also reports the two auxiliary-stream gates and byte lengths from
each record header without treating those separately supplied bytes as primary
trailing data. Both auxiliary gates and lengths are zero in this clear/triangle
capture.

`0x9d0`-byte main payload. It retains the payload pointer at render-command
`+0x18` and normalizes the source into these contiguous ranges:

`processRenderSetup` retains that same raw payload and passes
`payload + 0x2d0` to `copy3DCommonPassthroughData`. The leaf consumes a
`0x3ec`-byte common record and scatters 49 fixed ranges into the `0xc40`-byte

reduced to bit zero before being stored. The prefix size is independently
pinned by its typed allocator, and the call target, payload offset, complete
copy map, and boolean destinations are emitted as
`channels.descriptor_3d_common_passthrough`. Vinix implements the same
bounds-checked, template-preserving staging copy. This bridges raw validated
render input to the descriptor fields consumed by the HAL300 register graph;
the other `processRenderSetup` resource bindings and computed fields still
need equivalent producers.

The count is now derived from instructions rather than prose. The helper has
exactly eight `LDRB -> AND #1 -> STRB` chains, with eight unique source bytes
and eight unique descriptor destinations. Two other parser-masked booleans
fall inside the same raw `0x3ec` record: payload `+0x646` (common `+0x376`) is
also a validation operand, while payload `+0x650` (common `+0x380`) is retained
only in the parsed command. Neither is copied by this helper. Thus the helper
count is eight and the combined raw-record count is ten; there is no valid
nine-field interpretation. The generated JSON records this under
`boolean_accounting` and includes every masking instruction offset.

The selected render path actually allocates the `0x15b0`-byte
`AGXTACommandDescriptor` subclass and invokes its derived `init` after the 3D
base initializer. Recovery pins both allocators, the derived-to-base call,
the `+0x4b0..+0x800` base clear, 17 unique nonzero scalar defaults, and the
masks applied to qwords at `+0xc28` and `+0x14b0`. Vinix starts its host-only
staging object from a full clear and applies those scalar defaults. It
intentionally does not reproduce the Apple C++ vtables, embedded locks, or
retained `OSObject` pointers: those are host object lifetime state, not input
to a firmware work command.

The straight-line raw-payload work on either side of the common helper is
recovered separately as `channels.descriptor_ta_render_passthrough`. It
contains 20 pre-helper and 13 post-helper copy ranges plus 23 byte fields
reduced to bit zero. These writes cover both the base prefix and subclass tail
through `+0x15a8` against a validated `0x9d0`-byte payload. The direct ranges
include the contiguous payload `+0x30..+0x6f` state copied to descriptor
`+0x1050..+0x108f`. Resource lookup,
GPU-address translation, barriers, and computed fields in `processRenderSetup`
remain to be recovered before this staging object can become a firmware work
command.

The adjacent normalized-command stage is recovered independently as
`channels.descriptor_render_command_fields`. It performs eight direct writes:
five masked writes from four normalized bytes, one retained byte, and two
scalar ranges (command byte `+0x1b8` is deliberately written to two
destinations). A ninth descriptor write at
`+0xc38` selects literal one when normalized command byte `+0x283` is set and
otherwise uses bit zero of device-object byte `+0xf7e9`. Vinix implements the
same bounds-checked stage without embedding an Apple C++ object pointer in the
host-only staging descriptor. `IOGPUCommandDescriptor::init` proves that the
pointer at descriptor `+0x10` is the retained `IOGPU*` accelerator, while the
selected `configureDevice` path explicitly zeroes the halfword at accelerator
`+0xf7e8`; the fallback byte at `+0xf7e9` is consequently zero. This is the one
place where a count of nine is real: it counts descriptor writes in this later
stage, not boolean mask chains in `copy3DCommonPassthroughData`.

`AGXChannel::writeChannelCommandPointer` reserves one entry to distinguish a
full ring from an empty ring. It waits while `(write + 1) % ring_entries`
equals the firmware-owned read index, writes an 8-byte work-command GPU
address into the cached array, executes `dmb ish`, and only then publishes the
new write index at uncached offset `0x40`. `fw.enqueue_g17_channel_command`
implements the same publication order with release stores and returns `false`
instead of blocking if the ring is full or corrupt.

`AGXWorkQueue::submitCommandToFirmware` then builds a `0x18`-byte host-only
submit-info record. Its first word is the uncached control's write index read
after pointer publication; the firmware submitter narrows that word into the
outer data-master entry's 16-bit submission index. The remaining fields are a
host tracking sequence at `+0x04`, a channel counter at `+0x08`, zero padding
at `+0x0c`, and a selected metadata address at `+0x10`. Vinix's coupled queue
submission path locks and checks the outer ring before publishing the inner
pointer, carries the returned write index into the outer entry, and sends the
recovered doorbell only after both release-ordered publications succeed.

The outer flags byte is stateful. `encodeAcceleratorRingCommand` samples the
host channel byte at `+0x3c` and writes `1 & ~channel_flag`. The channel starts
clear, so its first accepted outer entry carries `1`; immediately after the
outer submitter succeeds, `submitCommandToFirmware` invokes vtable slot
`0x200`, whose concrete G17 implementation sets `channel+0x3c` to `1`.
Following entries therefore carry `0`. A priority change invokes slot `0x208`
to clear the byte again before its ordering barrier. Vinix retains the same
host-only state under the channel producer lock and advances it only after the
outer entry has become visible.

producer publishes its nonzero predicate at `0xfac`, so Vinix emits `1` there.
The following qword at `0xfb0` is the physical GPTBAT/TTBAT address. G17
vtable slot `0x11d0` selects `getGPTBATBase`, which obtains the GPTBAT memory
descriptor from the secure-monitor object and returns the same descriptor
physical-address helper used when programming the MMU. When the
`gptbat-ready` DeviceTree property is present, the selected PI_300 secure
monitor reads the 32-bit PFN from GPU register `0xd0802c` and shifts it left
by 14. On this Mac the independent `ttbat-phys-addr-base` value `0x47fffea`
therefore reconstructs `gpu-region-base=0x11ffffa8000` exactly. Vinix now
passes its validated UAT manager `ttbs_base` into the hardware-config builder
and publishes that physical address at `0xfb0`.
The final three scalar words are the GPU identity tuple copied from the
accelerator's `AGXGPUCoreConfig`: private core type `0x22` at `0xfb8`,
revision ID `4` (C0) at `0xfbc`, and active core count 40 at `0xfc0`. The G17

newest core branch produces `0x22` and whose C0 branch produces revision 4.
Independently, the live selector `0x100` `getDeviceConfig` output contains
`0x22`, `4`, and `40` at core-record offsets `0x20`, `0x24`, and `0x30`; the
base firmware producer copies the corresponding accelerator fields at
`0x4a0`, `0x4a4`, and `0x4b0` unchanged. Vinix keeps `0x22` as a separate
private core ID instead of confusing it with public generation 17.

The leading scalar record is now independently reproduced. Apple's selected
`retrieveChipInfo` method reads `chip-id` from `/chosen` and `chip-revision`
from `/arm-io`, then emits `{chip_id, revision >> 4, revision & 7, 0}`. The
ARM firmware-data producer copies that 16-byte record to `0xe90`. The live
Mac17,6 values are `{0x6050, 1, 1, 0}`, and Vinix now reads them from the same
DeviceTree properties instead of embedding the observed revision.

The native `perf-states` and `perf-states-sram` properties use Apple
little-endian `{frequency_hz, voltage_mv}` records rather than standard
big-endian FDT cells. On this machine they contain four tables of 14 states;
the maximum core frequency is 1620 MHz. Vinix now validates those dimensions,
cross-checks the frequencies between core and SRAM tables, and can populate
the recovered primary frequency, secondary SRAM frequency, and 16-column
voltage regions. The host reads the two frequency arrays at accelerator
offsets `0x1b318` and `0x1bb60`, applies the same reciprocal Hz-to-MHz
conversion, and writes hardware-config tables `0xfc8` and `0x1808`; Vinix now
reproduces both. The table at `0x1908` is also fully DeviceTree-backed: the
host parses `gpu-perf-base-pstate`, clears all entries, and records each boost
state as `100 * (frequency - base) / (maximum - base)`. On this Mac the base
state is 1 and the final entry is 100. Vinix now reproduces this relative
boost-frequency table. The host constructs a second curve at `0x1988` from
the AFR-domain state array using the same base index and normalization. The
named AFR fast-die producer independently anchors that source at accelerator
offsets `0x1c4e8`/`0x1c4f0`; Vinix reproduces the live 14-state curve, ending
at 100. G17's selected power-estimation virtual also takes an unconditional
feature-bit-17 path and fills one SRAM power-scale value per GPU performance
state. The raw float is `0x3f828f5c` (approximately 1.02); the base firmware
producer stages that row through runtime offset `0xc4`, and the ARM producer
copies all 16 slots to hardware-config offset `0x1848`. Vinix fills the active
14 slots and retains zero in the two unused slots. The adjacent static-power
row at `0x1888` is also resolved. The exact `AGXArmFirmwareASC` MetaClass path
requests its registered `0x2920`-byte type from `_OSObject_typed_operator_new`;
the matching live kernel takes the fixed-type branch with `Z_ZERO`. The SRAM
writer ends before source offset `0xd50`, the leakage writer begins at `0xe50`,
and G17 vtable slot `0xce0` selects a `bti; ret` static-power stub. Apple
therefore copies sixteen zero words from runtime offset `0x104`; Vinix retains
the same zero row.

The last two derived tables, `0x18c8` and `0x1948`, are now traced end to end,
and they are the first recovered rows that are *not* constants. Both are the
same 0..100 curve, normalised from a per-state power matrix with 32-bit
arithmetic: `100 * (row_sum(state) - row_sum(base)) / (row_sum(max) -
row_sum(base))`, base state 0. Apple produces `0x18c8` through a direct call to
`AGXAccelerator::populateLinearPowerTransferTable(config + 0x18c8, 0)` and
inlines the identical normalisation for `0x1948`. The `0x18c8` matrix lives at
accelerator `+0x1c630` with a `0x40`-byte row and `accel[0x4e4]` columns; the
`0x1948` matrix lives at `+0x1ca30` with an 8-byte row and `accel[0x4ec]`
columns. Unlike the neighbouring static-power row, G17 selects the real
producers: vtable slots `0xfd0` and `0xfd8` resolve to
`populateMaximumPerformancePower` and `populateMaximumPerformancePowerCS`,
and `populateMaximumPerformancePower` calls the CS producer first so the AFR
matrix is available when the primary matrix is built.

Both matrices come from an analog power model. Per state and per column Apple
computes `min(leakage(v) + coefficient * pow(v, exponent) * MHz, clamp) * v`,
where the primary matrix uses exponent `1.28`, coefficient `20.15` and clamp
`48500.0`, and the CS matrix uses exponent `1.0` with `21.7`/`38600.0` or
`12.29`/`24800.0` selected by the chip variant at `accel[0x4a0]`. The leakage
term is `calculateVddGpuLeakage` / `calculateAFRLeakage`, which pick one of
eight buckets from a static `0x58`-byte `LeakageParameters` record set and
evaluate `applyLeakageEquation` at a fixed 110 °C. That equation is linear in
its leakage input and multiplies it by four `pow` terms of voltage and
temperature; the matrix producer's separate dynamic term contributes the
fifth `pow` call on the primary rail.

`populateChipLeakageData` maps physical `0x23_8837_4000` for `0x1000` bytes;
only words `0x198`, `0x19c`, and `0x1a0` feed the selected decode. The eight
core selectors are `0,1,2,3,0,1,2,3`. Selectors 0/3 take bits 8..21 of word
`0x198`; selectors 1/2 join bits 22..31 of `0x198` with bits 0..3 of `0x19c`.
Every core adds bits 4..15 of `0x19c`, divided by four on G17C. The group value
is the twelve-bit field crossing bit 25 of the `0x19c:0x1a0` pair, multiplied
by two. Vinix maps the aperture as Device memory, reads those words with
volatile MMIO accesses, and retains the exact combined calibration in quarter
units. The analyzer publishes the complete four-record descriptor table and
both G17 scaling paths.

Those values are per-die binning data, so `0x18c8` and `0x1948` remain machine
specific. Vinix reads them at runtime rather than embedding a baseline row.
`generate_g17_power_model.py` factors the fused input out of the equation and
evaluates its nonlinear part off-line for the 29 voltages captured from this
Mac17,6. The generated Q24.40 tables are tied to AGXG17X UUID
`680ACC23-AB13-301C-B28A-3A2A257F7977`.

At runtime `fw.decode_g17_leakage_calibration` reproduces the fuse decode and
the power producer combines it with those factors. Small integer IEEE-754
helpers preserve Apple's exact binary32 conversion, multiplication, addition,
clamp, and truncation boundaries while the kernel remains `-nofloat`.
`fw.populate_g17_linear_power_transfer_tables` then reproduces both
normalisations with Apple's 32-bit arithmetic. The host-side tests compare the
integer path to native `pow`/`powf` results across every captured voltage,
every bucket boundary, and sampled fuse values; the ARM64 build additionally
checks that no floating-point code is introduced.

The adjacent `0x19c8` block is also complete. `getProbeScore` starts from a
zeroed chip-info record; the selected G17C readers do not write its map-enable
byte at `0x85`, and the selected `parsePerfStateMapRegs` virtual is a no-op.
Apple therefore takes its fixed fallback, placing `0..15` at accelerator
offset `0x1aa48` and sixteen zero words at `0x1aa88`. The ARM producer clears
the destination and copies those banks to hardware-config offsets `0x19c8`
and `0x1a08`. Vinix now emits the same two banks.

The G17-only `cs-perf-states` and `afr-perf-states` properties use a distinct
64-bit format: `{rail_count, state_count}`, followed by
`{voltage_uV, frequency_hz}` records for every rail and state, then one default
SRAM voltage per rail. Apple's producer divides voltages by 1000 and clamps
each SRAM voltage to `max(core_mv, default_sram_mv)`. Both live M5 Max records
have one rail, 14 states spanning 24 MHz through 1620 MHz, and a 775 mV SRAM
floor. The selected G17C `getPerfStateCap` method returns 14 for both domains.
The host copies the normalized tables into two typed `0x148`-byte hardware
configuration blocks at `0x1a48` (CS) and `0x1b90` (AFR); Vinix now validates
and reproduces both complete blocks.

### UAT handoff

The symbolized `AGXUnifiedAddressTranslator::initHandoff` routine establishes
the complete `0x648`-byte G17 uPPL handoff initialization. It writes magic
`0x4b1d000000000002` at `0x00`, clears byte locks at `0x10` and `0x11`, clears
the turn word at `0x14`, initializes the current slot at `0x18` to
`0xffffffff`, and clears 65 `0x18`-byte flush records beginning at `0x20`.
If the firmware magic at `0x08` differs, it writes byte `1` at `0x638`; the
tail qword at `0x640` is cleared. The G17 path does not wait for firmware to
mirror the magic as the older Linux-derived Vinix path did.

Vinix now selects this initialization by firmware ABI. G13 retains its
existing handshake, and T6050 remains blocked from hardware writes until the
remaining G17 bootstrap allocations and power sequence are implemented.

### Native T6050 power ownership

The Mac17,6 boot DeviceTree does not describe SGX power with Linux-style PMGR
power-domain nodes. Its `power-gates` and `clock-gates` properties both contain
the ordered handles `0x268, 0x267`. Resolving the public-handle field at byte
`0x1a` of the 48-byte PMGR `devices` records gives:

| Handle | PMGR record | Device |
| --- | ---: | --- |
| `0x268` | 572 | `GFX_SGX` |
| `0x267` | 575 | `GFX_BUSY` |
| `0x266` | 573 | `GFX_ASC` |
| `0x291` | 574 | `GFX_ASC1` |

The signed boot DeviceTree represents those records beneath both PMP wrapper
templates. Their `iop-nub,rtbuddy-v2` children name firmware `t6050pmp`,
publish die-strided 1 MiB regions, and assign AGX SoC-device ID `0x10`.
AppleARMPlatform loads the handle arrays and delegates their transitions to
AppleT6050PMGR; the gated T6050 implementation can cross into PMP firmware.
Consequently these handles must not be passed to Vinix's raw
`pmgr.enable_region()` register-offset path.

That static topology is not the active topology of this Mac17,6. The live
`arm-io` node reports little-endian `die-count = 1`, and the live DeviceTree
plane exposes only PMP0; a PMP1 lookup returns no node. The four GPU partitions
reported by `num_mgpus` all belong to that one die. `inspect_macos.py` now
records these values independently and rejects a PMP-wrapper count that does
not equal `die-count`. Vinix likewise uses `die-count` to admit and map only
active PMP/PTD apertures, while retaining two-die bounds for other T6050
configurations.

`recover_t6050_power.py` reproduces this result directly from the local
IMG4/LZFSE boot DeviceTree and rejects changed or ambiguous mappings. The
fileset extractor now retains AppleARMPlatform, ApplePMGR, AppleT6050PMGR,
ApplePMP, and ApplePMPFirmware so the command and service sides of this
boundary can be recovered against the same OS build. Hardware launch remains
gated until that PMP transition protocol and its readiness/error paths are
implemented.

The UUID-pinned ApplePMGR command path narrows that protocol further. Its PMP
v2 dispatcher routes commands 14 and 15 to the PTD dashboard. Both dashboard
branches accept only state 0 or 1 and obtain a selector from byte 3 of the
runtime PMGR device record. A flag-`0x10` record with a nonnegative byte at
`+0x0f` would select the virtual-device branch, but that predicate alone does
not make a record a command source. Both the initial-status walk and the two
dynamic enable/disable loops first require flag bit `0x02`.

This resolves the apparent selector-zero mismatch. The four leaf records
`GFX_SGX`, `GFX_BUSY`, `GFX_ASC`, and `GFX_ASC1` have flags `0x10`, selector
zero, and virtual class zero. They describe the GFX dependency graph but lack
bit `0x02`, so ApplePMGR never emits commands 14/15 for them. The aggregate
`GFX` record (index 357, public handle `0x16a`) has flags `0x02` and selector
`0x10`. It is the actual PMP command target: it takes the ordinary-device
branch and maps selector `0x10` to the PMP `AGX` record before operating the
`SOC-DEV-PS-REQ`/`SOC-DEV-PS-ACK` bitsets.

`initPMPv2` constructs the selector maps on the host. It initializes 257-entry
signed-u32 tables to `-1`, walks the 124-byte `soc-device` property, and writes
`device_index[record.id] = record_index`. A second table assigns dense indices
only to records whose word at `+0x2c` is nonzero. The standalone
`getPMPDeviceIndex` lookup adds the per-die selector stride, rejects values at
or above 256, and then reads the first table. PMP firmware does not publish
this translation to ApplePMGR.

The `t6050pmp` DeviceTree describes the backing bit ranges as:

| Range | ID | Bit offset | Bits |
| --- | ---: | ---: | ---: |
| `SOC-DEV-PKT` | 9 | `0x90` | `0x150` |
| `SOC-DEV-PS-REQ` | 10 | `0x1e0` | 8 |
| `SOC-DEV-PS-ACK` | 11 | `0x1e8` | 8 |

All three IDs are explicitly included in `pm-ptd-ranges`. The stripped PMP
firmware also walks the same records and multiplies their `+0x0c` field by
eight to assign SOC-DEV-PKT slices. The 37 live records consume 320 of the
range's 336 bits and leave 16 trailing bits reserved. AGX is SoC-device ID
`0x10`, record index 15, dense virtual-state index 3, and owns the eight-bit
slice `[0x1c0, 0x1c8)`. These four values are deliberately reported
separately: a PMGR handle, selector-map key, record index, and PTD entry are not
interchangeable.

PMGR's `ptd-ranges` binding is ordered `10, 11, 12, 13, 2, 4`, making the
fifth runtime range pointer (`this+0x72820`) PMP range ID 2. On this DeviceTree
that is `PMP-STATUS`: one bit at offset 1 with doorbell 16. The PMP-v2 wait
uses a per-die byte at `this+0x7283c`, sleeps through the command gate at
`this+0x1b80`, and reads the 64-bit `PMP-STATUS` entry through ApplePTD. A
nonzero entry latches the byte; `pmpReadyActionGated` also latches it and wakes
the command gate.

Dynamic device transitions have a verified ordering. When `checkNotifyPMP`
accepts the device, `enableDeviceGated` invokes virtual slot `0xac0` to wait
for PMP readiness before changing device status and before either command
14/15 emission loop. The initial device-status synchronization is different:
`initPMPv2` schedules it after constructing the selector tables, but the gated
callback itself has no explicit PMP readiness wait. It does call
`waitForClusterPowerUp` before each notification, but the UUID-pinned helper
only waits for dependent PMGR cluster-transition bytes through the command
gate; it neither reads ApplePTD nor calls the PMP-ready action.

The ordinary state routine supplies the missing initial-ordering rule. It
writes the persistent `SOC-DEV-PS-REQ` level before reading `PMP-STATUS`. If
status is zero, it stores zero in the selected die's ready byte and branches
to the successful return without reading `SOC-DEV-PS-ACK`. If status is
nonzero, it latches readiness and falls through to the acknowledgement loop.
Consequently initial synchronization may safely publish the desired level
before the service is ready; dynamic changes wait for readiness, while early
publication deliberately has no acknowledgement dependency. This does not
authorize Vinix MMIO yet: mapping ownership, serialization, timeout cleanup,
and the firmware-side handoff still need an implemented lifecycle.

The ordinary AGX state transaction is a read-modify-write of
`SOC-DEV-PS-REQ`, using `1 << soc-device record index` as its mask. State zero
clears that bit and state one sets it. The AGX record's state-flags word at
`+0x08` is `3`: bit 1 requires acknowledgement, while the clear bit 2 means an
enable does not bypass the wait. Thus both AGX directions synchronize. A
successful `SOC-DEV-PS-ACK` read must have bit 54 (`newData`) in its second
64-bit metadata word and must match the requested AGX bit in its first word.
The request remains at its requested level after success; there is only one
PTD write, not a pulse followed by a clear.

The acknowledgement loop has a 15-second fatal deadline. On expiry ApplePMGR
reads every entry in the `PMPTOOL` range and panics. It also computes and
recomputes a 100 ms deadline, but the recovered function never reads that
value and contains no sleep call; it visibly polls ApplePTD until new data and
a matching bit arrive. The recovery report states this oddity directly rather
than inventing a 100 ms polling cadence that the binary does not implement.

ApplePTD itself uses PMGR RegMap enum 8, but that enum is not a DeviceTree
`reg` array index. UUID-pinned `AppleT6050PMGR::initRegMaps` makes 60 ordered
`initRegMap` calls per die and maps enum 8 to `reg[7]`. On Mac17,6 that record
is a `0x40000`-byte aperture at `0x84240000`; PMGR's `die-stride` is
`0x4000000000`, so the two static PMP templates resolve PTD bases
`0x84240000` and `0x4084240000`. An implementation maps only those belonging
to active dies, and every mapped aperture must be Device MMIO.
The two static `t6050pmp` nubs also publish byte-identical 37-record `soc-device`,
`ptd-range`, and `pm-ptd-ranges` tables. Their 1 MiB shared regions are
`0x284500000` for PMP0 and `0x4284500000` for PMP1, again separated by exactly
one die stride.

The PMP wrappers themselves expose a separate four-region register topology.
PMP0 publishes `0x84e00000+0x88000`, `0x84850000+0x4000`,
`0x84500000+0x100000`, and `0x84250000+0x4000`; PMP1 adds the
`0x4000000000` die stride to every base without changing a size. Both wrappers
declare IOP version 1, `sram-index` 1, and PTD-update register index 3. The
AppleA7IOP code proves that `sram-index` is a provider power-domain selector,
not a DeviceTree register index. PMP0 IRQs are `0x18d,0x18c,0x18f,0x18e` with
gate IDs `0x1b,0x1c`; PMP1 IRQs are
`0xdad,0xdac,0xdaf,0xdae` with die-qualified gates
`0x1000001b,0x1000001c`. The recovery tool and kernel admission check now pin
all of these facts. None of the wrapper regions may be substituted with the
nub's shared region or PMGR's ApplePTD aperture. Concrete consumers now prove
the roles of wrapper registers 0, 1, and 3; register 2 remains unidentified.

The UUID-pinned ApplePMP and RTBuddy binaries now resolve the host attachment
edge for one of those regions. A separate UUID-pinned AppleA7IOP check proves
that `AppleWrapperMailbox::start` maps provider device-memory index 0 with
options 0, retains its memory-map object at `this+0x140`, and retains the
mapped virtual address at `this+0x100`. Its `_reg(unsigned int)` accessor then
loads one 32-bit value at that virtual address plus the zero-extended byte
offset. `getWrapperPhysicalAddress` obtains the physical address from the
same retained map. Thus T6050 wrapper `reg[0]` is the combined mailbox/control
Device-MMIO aperture, rather than ordinary memory or one of the other three
wrapper resources.

The `AppleA7IOP` class has the same index-0 register mapping and 32-bit byte-
offset accessor, retaining its map at `this+0x168`. Its `start` method reads
`sram-index`, stores the value at `this+0x15c`, and publishes
`should-control-sram` according to whether that selector is nonzero.
`enableSRAM(bool)` forwards the requested state and selector to
`_enablePower(bool, unsigned int)`, which passes the selector in `x3` to its
provider's power-state call. On T6050 the selector is 1. This expressly does
not identify a wrapper register by itself.

The UUID-pinned `AppleASCWrapV6` concrete subclass supplies the missing
consumer for wrapper `reg[1]`. Its initializer maps device-memory index 1 with
options 0, retains the map at `this+0x188`, and retains its virtual address at
`this+0x190`. On T6050 its IORVBAR byte offset is zero. `_setIORVBAR` performs
a 64-bit write of the firmware address OR lock bit 0, `_isIORVBARLocked` reads
that bit back, and the ordinary non-iBoot firmware-map path requires it to be
set. Therefore wrapper `reg[1]` is the IORVBAR Device-MMIO aperture.

The same binary closes the register-level CPU-start contract. Base
`AppleA7IOP::startCPUWithOptions` dispatches `_runCPU(true)` through vtable
slot `0xa28`. `AppleA7IOP::start` permits those writes unless the provider has
`cpu-ctrl-filtered`; neither T6050 PMP wrapper publishes that property. The
concrete method reads the 32-bit control register at `reg[0]+0x44`, sets bit 4
to run, and on stop clears bit 4, rereads, then clears bit 5. These facts prove
only IORVBAR and run-control register semantics. They do not prove the PMP has
executed the image, completed an RTKit handshake, or made its dashboard ready,
and they leave wrapper `reg[2]` unidentified.

Vinix mirrors that recovered register contract in a dormant per-die wrapper
transport. Its explicit constructor validates the native wrapper node before
mapping only `reg[0]` and `reg[1]` as Device memory. The IORVBAR operation
rejects a zero or already-tagged physical base, performs one locked 64-bit
write, and verifies bit 0 by reading it back. CPU start preserves all unrelated
control bits; CPU stop performs the recovered clear-bit-4, reread, clear-bit-5
sequence as separate accesses. The ordinary GPU probe does not construct this
transport, so validation remains read-only until firmware image ownership and
RTBuddy boot ordering are complete.

`ApplePMPv2::start` receives an
`RTBuddyEndpointService`, retains its endpoint from service offset `0x88`, and
calls `RTBuddyEndpoint::getSlaveProcessor`. Through the resulting
`AppleA7IOPNub`, it obtains the wrapper service, reads the
`ptd-update-reg-index` property, and fetches that exact device-memory entry.
On T6050 this proves wrapper `reg[3]` is the PTD-update memory resource. It
also obtains mapper index 1. Only after both resources are resolved does it
install the endpoint message callback, followed by the power-state callback.
This is an attachment contract, not a firmware boot or readiness signal; it
does not justify enabling the G17 hardware path.

The separate UUID-pinned `ApplePMPFirmware` image now closes the next part of
the firmware handoff without conflating it with readiness. Its service start
collects `board-id`, `dram-vendor-id`, `dram-capacity`, and
`dram-channel-disable` from `/chosen`; it collects `pmc`, two selected
`pmc-pmgr` bits, and `pmc-msg-disabled` from `/arm-io/pmgr`, plus
`soc-chip-variant`. Its `RTBuddyFirmwareService` vtable overrides slot `0x898`
with `ApplePMPFirmware::patchFirmware`. The function begins with exactly nine
unconditional 32-bit patchbay writes:

| Patch tag | Source |
| --- | --- |
| `BDID` | `board-id` |
| `DVID` | `dram-vendor-id` |
| `DCAP` | `dram-capacity` |
| `DCHD` | `dram-channel-disable` |
| `PMC_` | `pmc` |
| `PMCV` | `pmc-pmgr` bit 0 |
| `PMCB` | `pmc-pmgr` bit 3 |
| `PMCX` | `pmc-msg-disabled` |
| `CVAR` | `soc-chip-variant` |

These mandatory values precede the optional boot-argument-driven patches.
RTBuddy's recovered `fixup` order is: power on the target, call service slot
`0x890` (`preFirmwareLoad`), copy the image/create its coredump map when
needed, call service slot `0x898` (`patchFirmware`), run the registered
patchbay callback, update the patchbay and coredump view, publish the firmware,
and finally write the patchbay back to the target image. The gated loader then
sets RTBuddy's byte at `this+0x10b` and announces the firmware. That byte means
the image has completed RTBuddy's load bookkeeping; neither this function nor
the announcement establishes that PMP is executing or that `PMP-STATUS` is
ready. Vinix therefore still keeps all T6050 hardware writes behind the G17
admission gate.

The same pinned RTBuddy image now closes the next boundary without confusing
it with dashboard readiness. After a successful gated load, `loadFirmware`
requests RTBuddy power state 1 through vtable slot `0x818` unless its internal
transition-suppression byte is set. In the managed transition, RTBuddy records
IOP status 4, invokes the wrapper's `startCPUWithOptions` slot `0x888` with the
selected firmware, and immediately enters IOP validation. Validation either
polls the mailbox or blocks on the status word at `this+0x158`; both paths use
the timeout at `this+0x128`, accept their selected target status, and reject
the terminal status `0x8000` or a timeout.

The management-endpoint messages identify the ordinary initial target. Hello
is accepted at status 4 only when its advertised version interval contains
protocol 12, and advances RTBuddy to status 5. Endpoint roll call is accepted
at status 5; only after the host successfully sends its roll-call reply does
RTBuddy advance to status 6 and wake validation waiters. Status 6 is therefore
the first recovered RTKit transport/endpoint-discovery milestone after CPU
start. It is not ApplePMGR's independent `PMP-STATUS` PTD observation and not
an AGX device-state acknowledgement, so it still cannot open the G17 hardware
gate by itself.

The transport has distinct read and write layouts within each aperture.
`ApplePTD::readPTD` loads a 16-byte pair from `base + entry * 16`. The first
word is data. In the second raw word, bits 10..63 become decoded metadata bits
0..53, raw bit 1 becomes decoded bit 54 (`newData`), and raw bit 0 becomes
decoded bit 55; the caller's byte at output `+0x0f` supplies decoded bits
56..63. `ApplePTD::writePTD` instead performs one 64-bit store through
`ApplePMGR::writeReg64` at `base + 0x10000 + entry * 8`. The pinned read,
write, and final store sequences contain no explicit lock or DMB/DSB, so the
Device mapping supplies the required access ordering. Treating PTD as normal
cacheable RAM, using `reg[8]`, or writing through the read window would all be
incorrect.

Vinix now has this low-level ApplePTD transport encoded but dormant. Its
reader uses one AArch64 `ldp` for the data/raw-metadata pair, its writer uses
the separate 64-bit portal, both operations reject an out-of-range die or
entry, and pure helpers implement the recovered metadata, AGX request, and
acknowledgement rules. The internal T6050 admission check exercises the codec
and one-die/two-die bounds-failure paths without mapping or touching an
aperture. Mapping is still behind the G17 boot gate and maps only the active
die count. A nonblocking controller now serializes a request across the active
dies: `begin` holds an interrupt-disabling
spinlock only for request publication and the status sample, while each
`poll` holds it for one acknowledgement sample. Timeouts and errors after the
write are sticky because the request may have reached PMP; no unsafe retry or
invented reset sequence follows. The possible 15-second interval therefore
never runs with interrupts disabled.

For an ordinary device-state command ApplePMGR forms the selector-table key as
`DeviceData.selector + selector_die_stride * requested_die`, then forms the
request mask as `1 << returned_soc_device_record_index`. Object byte
`this+0x1bdc` bit 0 selects whether ApplePTD receives the requested die or die
zero. Thus the dashboard operation is explicitly per die on the multi-PMP
T6050; the two equal DeviceTree tables do not justify collapsing it to one
physical write.

Vinix's native T6050 probe now mirrors this as a read-only admission check. It
requires PMP version 2, the ordered PMGR range bindings, PMP0 plus PMP1 only
when `die-count` is two, the exact aggregate and leaf dispatch records, the
status doorbell, all four power ranges, and the derived PTD physical aperture
for every active die. It deliberately does not map those apertures or issue a
request; the G17 firmware boot gate remains closed.

The virtual-device writer combines per-device state into SOC-DEV-PKT and
writes the dense virtual-state PTD entry, but it is not the T6050 GFX proxy's
route. The recovery report now names the aggregate command target separately
from the four leaf gates and reports both the notification and dispatch
predicates. Dynamic readiness, the ordinary request/ack loop, and ApplePTD's
byte-accurate MMIO transport are now recovered, including the pre-ready
request rule. The kernel-side serialized transaction is implemented but not
instantiated; PMP service integration, reset recovery, and firmware handoff
still need to establish when Vinix owns the apertures and may issue a GFX
transition, so the native hardware gate remains closed.

The matching ApplePMP entry (UUID
`AA65CE02-93C8-33DE-A7BE-B11E1621F739`) supplies a second, independent
boundary check. `ApplePMPv2::start` installs a message callback on its RTBuddy
service at object offset `+0x88`. Incoming 64-bit words carry a four-bit class
at bits 52..55: class 1 is memory, class 2 is power, and classes 3/4 are
registry traffic. The generic send method passes exactly one 64-bit word
through the RTBuddy vtable slot at `+0x1e8`.

The class-2 exchange visible here is a ping, not the missing AGX state-ready
event. `pingGated` sends class 2 with the low 32 bits of a host timestamp,
marks byte `this+0x108` in flight, and sleeps on that byte. PM subtype 1 clears
the byte and wakes its sleepers. ApplePMP also exposes an indexed 64-bit
diagnostic dashboard writer configured by `pmptool-config`; that is distinct
from ApplePMGR's `SOC-DEV-PS-REQ`/virtual-state operation. The recovery JSON
states both scope limits explicitly, preventing either path from being used as
evidence to open the hardware gate. The still-missing proof is the ordering
between PMP service readiness and ApplePMGR's separately scheduled initial
device-status callback; the native kernel also still lacks a safe PTD owner.

The installed `t6050pmp` recovery image is a `pmpf` IM4P containing an ARM64
`MH_PRELOAD` Mach-O (UUID `ED70AC90-9087-3857-B454-318E50A9223F`). It has an
empty symbol table and no `LC_FUNCTION_STARTS` command, so firmware routines
must be bounded from their control flow rather than inferred symbol metadata.
`extract_pmp_firmware.py` makes that stripped-image boundary explicit and
produces a hash-pinned local analysis input under the ignored `build/` tree;
no Apple firmware bytes are committed.

The extracted image has `__TEXT` at IOP VA `0x1000000` for `0x5e000` bytes and
`__DATA` at `0x105e000` for `0x9a000` bytes, occupying `0xf8000` of the 1 MiB
PMP region. Live PMP0 publishes the corresponding two native-endian
`segment-ranges`: physical/remap `0x284500000` with flags 3 for text, followed
by `0x28455e000` with flags 6 for data. These properties are absent from the
signed recovery DeviceTree and present in the live DeviceTree plane, so they
are treated as runtime preload evidence rather than as part of the static
template. Vinix decodes that descriptor without mapping or reading the image;
the wrapper still remains dormant until the image owner and RTKit lifecycle
are complete.

Vinix now performs the same ownership checks during native T6050 probe. It
validates both SGX and ASC gate arrays, their unique named PMGR records, every
active PMP's RTKit/preload identity, and the three dashboard ranges. This stage
is read-only and runs before the existing whole-ABI hardware gate; it does not
start PMP or map, read, or write a PMP/PMGR register.

The active boot kernel collection contains arm64e fileset entries for
`com.apple.AGXG17X` (UUID `680ACC23-AB13-301C-B28A-3A2A257F7977`) and the G17
firmware buddy (UUID `93F44AA7-63B3-3D75-8A9E-E4095ABBDD1D`). The former has
6,545 symbols, including named firmware allocation, initialization, UAT, and
channel routines. The extractor also materializes the matching kernel entry
(UUID `FF5FFF89-5F93-3D5F-A4FB-74B8C8C313AC`) so allocator calls can be
resolved against their implementation. `extract_fileset.py` unwraps the local
IMG4/LZFSE collection and rebases its collection-relative segments and shared
symbol table into standalone Mach-Os. No Apple executable is committed.

## Upstream implementation boundary

The Apple Silicon kernel, bootloader, and Mesa trees audited on 2026-09-04 do
not implement this GPU:

- Linux Asahi `asahi` at `77cb8f2` and `gpu-next` at `84850f2` select G13/G14,
  not T6050/G17.
- m1n1 at `940439` recognizes T6050 as an SoC but its GPU boot handoff supports
  only T8103, T60xx, and T602x families.
- Mesa at `dc886f3` contains a newer `AGX2.xml` ISA description, but its Asahi
  device selection still covers G13/G14 and the official DRM UAPI does not
  match Vinix's provisional private ioctl layout.

Accordingly, `t6050_config()` is a discovery configuration and
`can_boot_firmware()` returns false. Removing that gate before implementing
and validating the G17 firmware, UAT/DART, power-controller integration, and
command ABIs is not a supported bring-up step.
