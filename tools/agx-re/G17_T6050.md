# T6050 / G17C bring-up notes

Observations below are from a Mac17,6 with an Apple M5 Max running macOS 26.5
(25F71), AGXG17X 351.2. They are versioned facts, not assumptions that every
G17 machine has the same topology.

## Hardware identity

| Property | Observed value |
|---|---:|
| Apple DeviceTree compatible | `gpu,t6050` |
| GPU generation / variant | 17 / C |
| GPU cores | 40 |
| GPU partitions (`num_mgpus`) | 4 |
| Core masks | `0x3ff`, `0x3ff`, `0x3ff`, `0x3ff` |
| Fragment units | 40 |
| Geometry processors | 16 |
| USC generation | 3 |
| Kick queue mask / shift | `0x7f` / 40 |
| Performance states | 14 entries, base state 1 |
| System/GPU timestamp timebase | 24 MHz |

The two `sgx` register ranges reported by the Apple DeviceTree are
`0x2300000000 + 0x03fdc000` and `0x2300d00000 + 0x00177000`. Vinix must take
these from the boot-time device tree; they are recorded here only to make bad
hard-coded addresses obvious during review.

The corresponding `/arm-io/gfx-asc` node is `iop,ascwrap-v6`. Its first
register window is `0x2102600000 + 0x88000` before parent-bus translation.
The preloaded firmware mappings reported in `segment-ranges` are:

| Segment | Physical | RTKit IOVA | Size |
|---|---:|---:|---:|
| `__TEXT` | `0x10001000000` | `0xfffffc0000000000` | `0x4c000` |
| `__DATA` | `0x100026f0000` | `0xfffffc000004c000` | `0x130000` |

The ranges are virtually contiguous. The `__DATA` physical address and size
equal the independent `sgx` `gfx-data-base` and `gfx-data-size` properties.
`inspect_macos.py` now rejects drift in those relationships.

The native UAT reservations are also explicit in this tree: a `0x4000`-byte
handoff at `0x11ffff20000`, a `0x80000`-byte shared page-table region at
`0x11ffff28000`, and a `0x4000`-byte 64-context TTB table at
`0x11ffffa8000`. The `ttbat-phys-addr-base` value `0x47fffea` is exactly the
TTB physical base shifted right by the 14-bit UAT page size. G17 uses a
42-bit input address space (root/middle/leaf shifts `36/25/14`) and 16 KiB
table pages. Vinix now consumes these reserved regions and implements the
firmware's `0x648`-byte uPPL handoff structure instead of allocating an
unrelated page or treating AGX as a DART client.

The local AGXG17X 351.2 kernel implementation independently confirms the
handoff offsets. Its named `AGXUnifiedAddressTranslator::initHandoff` routine
writes `0x4b1d000000000002` at offset `0`, uses firmware magic at `0x8`, byte
locks at `0x10`/`0x11`, the turn at `0x14`, and the current slot at `0x18`.
It clears 65 24-byte flush records starting at `0x20`, followed by fields at
`0x638` and `0x640`. This is exactly `0x648` bytes; the surrounding reserved
page is larger. On a fresh handoff the Apple driver initializes the current
slot to `UINT32_MAX` and sets byte `0x638` when the firmware-side magic is not
already present. Firmware readiness remains a separate phase of bring-up.

## Device user-client ABI

An off-screen Metal triangle opens `AGXAcceleratorG17X` with type `0x100005`.
The AGX-specific selectors used during startup are:

| Selector | Kernel symbol | Input | Output |
|---:|---|---:|---:|
| `0x100` | `getDeviceConfig` | 0 | 152 bytes |
| `0x102` | `getDriverInfo` | 0 | 456 bytes |
| `0x105` | `performanceCounterSamplerControl` | 72 bytes | 72 bytes |
| `0x107` | `setDeviceNotificationPort` | async | 0 |

Selectors below `0x100` are implemented by the IOGPU superclass. The same
run queried selectors 0, 2, 5, and 6 with output sizes 64, 536, 32, and 16
bytes respectively. Run `make -f GNUmakefile trace` to reproduce the list on
the current operating system.

The `AGXDeviceUserClient::getTargetAndMethodForIndex` table also names
selectors through `0x112`; `agx_trace.c` annotates those names in JSON output.

## Metal command encoding

The installed userspace driver identifies the device as `AGXG17CDevice` and
uses `AGXG17XFamilyCommandQueue`, `AGXG17XFamilyCommandBuffer`, and
`AGXG17XFamilyRenderContext`. Its internal C++ templates select `HAL300`.

Private IOGPU storage calls bracket one 2,752-byte (`0xac0`) segment for both
an empty clear and the triangle. In a same-process pair only 50 bytes in 33
runs differ. The segment begins with `0x00000ac000010000` as a little-endian
64-bit word; disassembly of `AGX::ContextCommon<HAL300>::newCommand` agrees
that `0xac0` is the segment size. These observations are reproducible with
`make -f GNUmakefile trace`; they are not yet a complete work-command ABI.

Resource tracing resolves addresses in the segment only against allocations
already exposed to the process by `IOGPUMetalResource`. In the observed pair,
the clear references offset `0x400` and the triangle offset `0x100` in the same
32 KiB allocation. The two snapshots differ in 794 bytes. A triangle-only
128 KiB allocation is also referenced, consistent with pipeline/shader state.
The GPU virtual addresses are allocation-run observations, not constants to
copy into Vinix.

## Vinix userspace boundary

Vinix pins Mesa 25.0.5. Its Asahi interface is an explicitly unstable UAPI,
so `kernel/modules/drm/ioctl/ioctl.v` mirrors that version byte-for-byte: the
global parameter block is `0x1b0` bytes, a top-level command is `0x38`, and a
render command is `0x1d0`. The kernel validates every structure size before
registering an AGX DRM device. The core DRM path also supplies version,
capability, GEM-close, binary-syncobj, and GEM mmap services needed by libdrm.

This contract does not make Mesa 25.0.5 a G17 compiler. That Mesa release
selects only G13/G14 device backends and would mis-encode G17 as G14X. Vinix
therefore rejects real command submission with `EOPNOTSUPP`, and the T6050
firmware boot gate remains closed, until the HAL300 shader and work-command
encoders are recovered. The previous Vinix ioctl accepted a made-up compact
render structure unrelated to Mesa; it has been removed rather than exposed
to hardware.

## Firmware boundary

The G17 firmware is supplied by `AGXFirmwareKextG17XRTBuddy`, not by the
macOS 12.3 G13 ABI modeled in `kernel/modules/gpu/agx/fw`. The local recovery
volume contains two G17X IM4P containers. Each has a G17S (`a010`) and G17C
(`a000`) Mach-O; `extract_firmware.py` deterministically selects `a000`.

| Role | Bytes | Mach-O UUID | Virtual end |
|---|---:|---|---:|
| `armfw_g17x` | 1,579,528 | `0EDFE976-E37B-3E68-9D64-E3ABF7772D11` | `0xfffffc000017c000` |
| `armfw1_g17x` | 1,612,328 | `E324121D-8058-361E-9169-FCDE40123948` | `0xfffffc0000184000` |

Both images identify `RTKit-3255.120.11.release`, firmware generation G17,
build variant G17C A0, and SKSM support. Diagnostic strings explicitly reject
a host/firmware interface mismatch and distinguish host-mapped firmware
allocations. The primary virtual size (`0x17c000`) and the second role's extra
`0x8000` agree with sizes independently recovered from the firmware buddy.
The modern driver also contains AGFI scheduler/channel types absent from the
existing Vinix structures.

Disassembly of the primary image's endpoint-`0x20` bootstrap handler provides
the first byte-accurate root anchors:

- the init message matches `(message & 0x00bf000000000000) ==
  0x0081000000000000`, with the root IOVA in the low 44 bits;
- the first root word must equal `0x0c8bc322072804c0` or firmware aborts with
  the host-interface mismatch diagnostic;
- firmware copies the first `0xc8` bytes, then requires the 32-bit field at
  offset `0x2c` to be nonzero for host-mapped allocations.

The symbolized local `AGXArmFirmware::initFirmwareData` routine independently
confirms the complete top-level pointer placement. It constructs separate
roots for firmware roles 0 and 1, writes the role at `0x28`, and writes `1` at
`0x2c`. The corresponding firmware handler copies and consumes these fields:

Each root occupies its own 16 KiB host allocation, rounded to and aligned on
the M5's 16 KiB kernel page. Role 0 keeps its CPU/GPU mapping objects at host
members `0x19e0`/`0x19e8`; role 1 uses `0x1a18`/`0x1a20`. The CPU address is
obtained through mapping vtable offset `0x138` while building the headers, and
both firmware-GPU mappings are explicitly prepared before boot and completed
afterward. `fw.G17BootstrapPage` and `initialize_g17_bootstrap_page` now model
and deterministically clear the complete allocation rather than copying an
unbacked `0xc8` header.

| Root offset | Host allocation | Observed role |
|---:|---:|---:|
| `0x08` | bootstrap region from host member `0x1a58` | both |
| `0x18` | firmware shared data (`0x4c0` bytes; GPU members `0xab8` / `0xbe8`) | role 0 / 1 |
| `0x20` | runtime data (`0x1ca0` bytes; GPU member `0x388`) | both |
| `0x30..0x97` | platform configuration block | both |
| `0xa8` | small shared data (`0x20` bytes; GPU members `0xad0` / `0xc00`) | role 0 / 1 |
| `0xb0` | primary region (`0xe440` bytes; GPU member `0xce0`) | role 0 |
| `0xb8` | secondary region (`0x6f0` bytes; GPU member `0xce8`) | role 1 |
| `0xc0` | secondary auxiliary region (`0xa8` bytes; GPU member `0x398`) | role 1 |

The two small shared records at root offset `0xa8` have a complete 32-byte
layout. Their host-owned words are ktrace state at `0x00`, host-ready `1` at
`0x04`, and the system-sleep notification at `0x08`. Firmware publishes its
power state at `0x10` and monotonically observed ASC power generation at
`0x1c`; host wait/snapshot routines consume those exact words for both roles.
Offsets `0x0c`, `0x14`, and `0x18` remain reserved. Vinix now constructs the
host-owned initial state and leaves the firmware-owned/reserved words zero.

The single runtime allocation at root offset `0x20` is shared by both roles.
Its `0x1ca0`-byte size is not sufficient to construct it: four symbolized
initializers populate it from host policy and platform state. The recovered
producer establishes these larger regions:

| Runtime range | Bytes | Producer source |
|---:|---:|---|
| `0x054..0x059` | `0x6` | accelerator halfwords at `0x768..0x76d` |
| `0x0a4..0x0e3` | `0x40` | firmware host object at `0x27c8` |
| `0x0ec..0x7c3` | `0x6d8` | complete power-controller snapshot |
| `0x7c4..0x7eb` | `0x28` | Smart Idle policy at `0xe948..0xe96f` |

The power-controller snapshot is rearranged rather than copied linearly. Two
64-qword tables from source offsets `0` and `0x248` land at runtime offsets
`0x26c` and `0x4b4`; the surrounding scalar copies cover the rest of the
destination range without holes. On the pinned G17C driver, accelerator
vtable slot `0xd80` resolves to
`AGXAccelerator::populateDPEPPTConfigData`. That complete implementation
clears `0x6e0` bytes at source offset `0x5c`; the snapshot reads only source
offsets `0x60..0x737`. Runtime `0x0ec..0x7c3` is therefore proven to start
entirely zero, and Vinix now initializes that exact range explicitly.

The earlier 64-byte performance-controller slot has a separate lifetime.
`AGXArmFirmware::setupConfig` explicitly clears all 57 meaningful source bytes
at host-object offsets `0x27c8..0x2800`; the seven remaining copied bytes are
alignment padding. The runtime snapshot therefore begins with no controller
or boost override active. Vinix reproduces those zero values and clears the
reserved tail deterministically. This does not discard the M5 Max boost
policy: the firmware getters fall back to the accelerator's DeviceTree-backed
minimum-utilization and CE-step values while the runtime override-valid fields
remain unset.

The G17 accelerator vtable also selects the checked PI_300 `configureDevice`
and `configurePowerAndPerformanceController` override chain. The former
installs platform halfwords `ffff, 0028, ffff`. The latter replaces the base
Smart Idle delay with `1500` microseconds and the minimum-confidence value
with IEEE-754 `0.6`; the remaining recovered values are `1.0, 0.8, 0.2, 0.9,
0.1, 0.25, 0.9`, followed by a reset count converted by the firmware from
integer `6` to float `6.0`. Vinix writes the resulting 40 runtime bytes
directly. The source is accelerator offset `0xe948`, not `0xf948`; the ARM
initializer forms an `accelerator+0xe000` base before its `0x948` loads.

The same recovery verifies deterministic startup words throughout the
object. In particular, `0xa04..0xa2b` is cleared; the callback result at
`0x1c2c` and the normalized role count at `0x1c41` are dynamic;
`0x1c45..0x1c50` is cleared; and the four unaligned RIART words at `0x1c81`,
`0x1c85`, `0x1c89`, and `0x1c8d` start as `1, 0, 0, 0`. Short symbolized
accessors independently fix the register-override table at `0x804` (16
records of `0x18` bytes, count at `0x984`), progress/timeout controls at
`0x99c..0x9dc`, four six-byte firmware-utilization records at `0x9eb`, and
keepalive controls at `0x1c30..0x1c3f`.

The role-0 firmware immediately dereferences the allocation at `0x18`; its
first word leads to the large hardware/configuration payload. These names are
allocation-level descriptions only: none imply compatibility with the older
G13 nested structures.

The platform block is an exact `0x68`-byte copy from the object reached
through host member `0x298` and pointer offset `0x1a948`. It is copied into
both roots without role-specific changes. The pointer is the G17 legacy
shared-GART backing object, whose vtable slot `0x178` resolves to the cloned
PI-300 `initGartInfo` implementation. That producer initializes every byte in
the copied range at object offsets `0x18..0x7f`: the recovery tool verifies
its scalar literals, three identical 16-byte range descriptors, 16 KiB page
parameters, and fixed address-range values. `fw.G17PlatformConfig` now
constructs that exact byte sequence. Individual field semantics remain
conservatively unnamed, and root bytes `0x98..0xa7` remain opaque.

The object at root offset `0x08` is now independently recoverable. The host
allocates a 4 KiB requested payload rounded to the G17 firmware's 16 KiB page,
keeps its CPU mapping at member `0x1a50` and GPU mapping at `0x1a58`, and
publishes the firmware-converted GPU address to both roots. Its preparation
cursor is a 32-bit byte offset at host member `0x1ac0`.

The buffer is a sequence of `0x18`-byte register records:

| Offset | Bytes | Meaning |
|---:|---:|---|
| `0x00` | 8 | value or physical address |
| `0x08` | 4 | register |
| `0x0c` | 4 | auxiliary value |
| `0x10` | 4 | record kind |
| `0x14` | 4 | untouched padding |

Kinds `1`, `2`, and `3` encode 32-bit writes, 64-bit writes, and 64-bit
physical-address writes. Kind `0` terminates the sequence. Before boot, the
driver resets the cursor, invokes accelerator vtable slot `0xa88`, then
appends a terminator whose first `0x14` bytes are zero. In the pinned G17X
vtable that slot resolves through its authenticated kernel rebase to
`AGXAccelerator::populateInitSequenceFirmware(unsigned char).8148`; the
entire implementation is `bti c; ret`. T6050 therefore contributes no
register writes, and the safe Vinix representation of this region is a
zero-initialized 16 KiB mapping beginning with the kind-zero terminator.

The driver's allocation descriptors independently establish the exact sizes
of every object published directly through a root. The `0x4c0` shared object
contains host-written addresses at `0x00`, `0x08`, `0x10`, and `0x200`, a
five-address cluster beginning at the deliberately unaligned offset `0x254`,
additional addresses from `0x2d0` through `0x2f0`, a state byte at `0x3e0`,
a `0x90`-byte status area at `0x3e1`, a role-1-only address at `0x471`, and a
16-byte calibration value at `0x479`. G17-only packed structures now preserve
those offsets and keep all unknown ranges opaque.

Within each shared object, offsets `0x1a0`, `0x1a8`, `0x1b0`, and `0x1b8`
publish the accelerator ring's read-index, CFI-index, write-index, and entry
GPU addresses. Eight additional GPU addresses occupy `0x1c0..0x1f8`; their
allocation bindings are recovered, but their firmware semantics remain
unnamed. The exact direct publications recovered from
`AGXArmFirmware::initFirmwareSharedData` are:

| Shared offset | Role 0 GPU member / bytes | Role 1 GPU member / bytes |
|---:|---:|---:|
| `0x000` | `0x300` / `0x2710` | `0x300` / `0x2710` |
| `0x008` | `0x338` / absent (`0` bytes) | `0x338` / absent (`0` bytes) |
| `0x010` | `0x340` / `0x88` | `0x340` / `0x88` |
| `0x200` | `0xac0` / `0x79800` | `0xbf0` / `0x79800` |
| `0x254` | `0x308` / `0xc18` | - |
| `0x25c` | `0x310` / `0x1048` | - |
| `0x264` | `0x318` / `0xe10` | - |
| `0x26c` | `0x328` / `0x68` | - |
| `0x274` | `0x330` / `0x800` | - |
| `0x471` | - | `0x320` / `0x11dd0` |

The `0x338` output belongs to the firmware BRN-workaround-table allocation
descriptor (`0x2f0` CPU / `0x338` GPU). Its size comes from accelerator vtable
slot `0xf90`, which resolves on G17X to
`getSizeOfFWBRNTable().8051`. That implementation returns zero. The G17
firmware vtable's address converter at slot `0x2d8` is also an identity
function, so both shared objects intentionally contain zero at `0x008`; no
BRN table is allocated or populated on T6050. Role 0 may additionally publish
an address at `0x2d0` when the platform flag at `0xf754` is set; its source is
the pointer at platform offset `0x13768`.

Four further optional service addresses are produced from platform pointers
at `0x11560` and `0x11568` and written to role 0 offsets `0x2d8`, `0x2e0`,
`0x2e8`, and `0x2f0`. Role 1 mirrors the role-0 values at `0x2d8` and
`0x2e8`; both roles explicitly clear `0x2f8`. Each service pointer is
nullable in the pinned producer. A missing outer service clears the first
address of its pair, while a missing nested object at member `0x58` produces
a zero second address. The non-null mapping objects expose their GPU address
through vtable slot `0x158`. Vinix may therefore leave all four service
addresses zero when it does not instantiate those optional services.
Platform scalars at `0xf7c0`
and `0xf834` populate role 1 offset `0x300` and role 0 offset `0x304`,
respectively. Both roles copy the same 16-byte platform calibration block
from `0xf790` to the deliberately unaligned offset `0x479`. Finally, role 0
sets its byte at `0x3e0` to `0xff` and clears the following `0x90`-byte status
area. The G17 vtable's selected `halGetDefaultUscMaxTgmem` implementation
returns 12, which `configureDevice` stores at `0xf7c0`. The `0xf834` GVDM-mode
field retains its zero/default sentinel during bootstrap; its only direct
writer is `setGVDMMode`, called later by two performance-counter access paths.
The same base configure path explicitly clears all 16 calibration bytes at
`0xf790`, and the PI_300/G17 override chain does not replace them. Vinix now
publishes values 12 and 0 to the two role-specific scalar fields and leaves
both calibration copies zero. The optional service objects' semantic names
remain unknown.

The auxiliary publications at `0x1c0..0x1f8`, in order, come from GPU members
`0xb40`, `0xb60`, `0xb48`, `0xb68`, `0xb50`, `0xb70`, `0xb58`, and `0xb78`
for role 0. Role 1 uses `0xc70`, `0xc90`, `0xc78`, `0xc98`, `0xc80`, `0xca0`,
`0xc88`, and `0xca8`. Their corresponding sizes are `0x30`, `0x4800`,
`0x1b0`, `0x28800`, `0x30`, `0x9000`, `0x30`, and `0x4800` bytes.

Vinix now has a separate G17 ownership graph which allocates all of these
objects with 16 KiB alignment, maps them through the native UAT, publishes
the accelerator and auxiliary addresses in their role-specific shared
objects, initializes the recovered role-0 sentinels, and builds both root
pages. The shared platform values and runtime DPE/PPT policy are now complete.
The graph deliberately reports itself unbootable after construction because
hardware-configuration scalar/derived tables, firmware channel construction,
and work-command producers remain incomplete. This fail-closed path prevents
the older G13 channel or InitData layouts from reaching `MSG_INIT` on T6050.

Three nonzero allocations have fully recovered initial contents even though
their later field semantics remain unnamed. `AGXFirmware::initFirmwareData`
clears every byte of the role-0 `0x68`-byte allocation published at `0x26c`,
the role-0 `0x800`-byte allocation published at `0x274`, and the `0x88`-byte
shared-control allocation published at `0x010` in both roles. Dedicated G17
types and zero constructors represent these objects without borrowing an
older firmware generation's layout.

The other three role-0 bootstrap allocations are also initialized without
platform-dependent data. The `0xc18`-byte object at shared offset `0x254` and
the `0xe10`-byte object at `0x264` remain fully zero. The `0x1048`-byte object
at `0x25c` is cleared and then receives `0xffffffff` sentinels at offsets
`0xa18` and `0xa30`. Together with the zero regions at `0x26c` and `0x274`,
this establishes the complete initial contents of the five-address role-0
cluster.

`fw.G17BootstrapHeader` records the verified top-level fields and treats the
platform block as an explicit typed input. `fw.initialize_g17_bootstrap_region`
constructs the now-verified root-offset-`0x08` target.
`fw.G17FirmwareSharedBindings` likewise requires all recovered mandatory
publications before constructing either role's shared object. The remaining
bytes and nested allocation contents stay opaque, and `can_boot_firmware()`
remains false for G17.

### Accelerator rings

The local G17 driver no longer submits the legacy G13 work messages currently
modeled by Vinix. Its named `AGXAcceleratorRing` accessors establish a
`0x30`-byte shared state with 256-entry indices at these offsets:

| Offset | Field |
|---:|---|
| `0x00` | read index |
| `0x10` | CFI/completion index |
| `0x20` | write index |

`AGXArmFirmware::encodeAcceleratorRingCommand` and the ring enqueue routines
also establish a `0x18`-byte data-master entry and a `0x40`-byte device-control
entry. The data-master fields currently proven are the channel data address at
`0x08`, command type at `0x10`, submission index at `0x14`, channel ID at
`0x16`, and flags at `0x17`. These are represented by G17-only structures;
the legacy Vinix channel path is not reused for T6050.

The host-side ring object is five qwords: its dispatch table followed by CPU
and GPU addresses for the `0x30`-byte state allocation, then CPU and GPU
addresses for a `0x4000`-byte entry allocation. Role 0 binds this object at
host member `0xad8` and role 1 at `0xc08`. The recovery tool validates both
allocation pairs and all four firmware-visible published addresses.

Each later work context has a second level of channel state. The base
`AGXChannel::resetChannelState` implementation proves a `0xc0`-byte state
object, a `0x70`-byte uncached control header, and an 8-byte cached command
pointer stride. Host channel members `0x58`/`0x60`/`0x68` hold the CPU
addresses for state, uncached control, and cached commands; members
`0x80`/`0x88`/`0x90` hold their corresponding GPU addresses. The outer data
master entry publishes the state GPU address from member `0x80`.

The state object starts with uncached and cached GPU addresses at `0x00` and
`0x08`. Its checked reset fields include a context cookie at `0x10`, mode 4
at `0x28`, `0xffffffff` sentinels at `0x24` and `0x44`, a platform value at
`0x48`, and an unaligned platform address at `0x9c`. The uncached header keeps
its read and write indices at `0x00` and `0x40`, a `0xffffffff` sentinel at
`0x50`, and the ring-entry count at `0x60`.

The firmware resource pools live at host firmware members `0x11c8` (state),
`0x1348` (uncached), and `0x1408` (cached). The latter two use the recovered
element-size formula `0x70 + configured_queues * 0x80`, with distinct cache
attributes. `fw.initialize_g17_channel` now constructs the checked portion of
all three mappings, but requires the still-unnamed platform value/address as
explicit inputs. Work command formats and the source of those inputs remain
bring-up blockers.

`AGXChannel::writeChannelCommandPointer` reserves one entry to distinguish a
full ring from an empty ring. It waits while `(write + 1) % ring_entries`
equals the firmware-owned read index, writes an 8-byte work-command GPU
address into the cached array, executes `dmb ish`, and only then publishes the
new write index at uncached offset `0x40`. `fw.enqueue_g17_channel_command`
implements the same publication order with release stores and returns `false`
instead of blocking if the ring is full or corrupt.

### Hardware configuration allocation

The firmware allocation descriptors establish one `0x2710`-byte object at
host CPU/GPU members `0x2b8`/`0x300`. `AGXArmFirmware::initFirmwareSharedData`
publishes the same GPU address at offset zero of both role-specific shared
objects. The primary firmware dereferences that address while handling the
initialization message.

The recovery tool decodes 125 fixed or loop-indexed loads from that handler
and rejects changes to representative anchors across the object. It also
checks the corresponding producer loops in the symbolized driver. Those loops
establish 64 color-conversion records at `0x38`, split into two 32-record
banks; 53 modern `0x28`-byte I/O-mapping records at `0x640`; and a maximum of
16 performance states. The maximum state index is at `0xfc4`, followed by
16 frequencies at `0xfc8`, 16 rows of 16 voltages at `0x1008`, a matching
SRAM-voltage table at `0x1408`, and 16 secondary frequencies at `0x1808`.
Five further 16-entry derived tables begin at `0x1848`, `0x1888`, `0x18c8`,
`0x1908`, and `0x1948`.

The complete 56-byte prefix before the matrices is now independently checked
against `AGXFirmware::initFirmwareData`:

| Offset | Value | Recovered role |
|---:|---:|---|
| `0x00` | `0x0000006f00000000` | userspace VA map parameter |
| `0x08` | `0x00000000ffc00000` | userspace VA limit parameter |
| `0x10` | `0x0000001000000000` | USC start |
| `0x18` | `0x0000001000000000` | second USC start |
| `0x20` | `0x000002ffffff8000` | unknown-page address |
| `0x28` | `0xfffffc2181400000` | timestamp-area base |
| `0x30` | `0` | optional YUV CSC table address |

The first two words come from the exact read-only vector loaded by the host;
the remaining nonzero values are materialized in the producer. The timestamp
address passes through the G17C identity firmware-address converter and begins
exactly where GART range 10 ends. The G17 accelerator's vtable slot `0xf40`
selects a three-instruction `setupCSCAllocation` override which returns success
without allocating a table, and the later null path writes zero at `0x30`.
Vinix now uses a typed `G17AddressSpaceLayout` for all seven words.

The matrix source is also fixed for this driver. G17 vtable slot `0xfb8`
selects the 116-byte PI_300 `generateCSCCoefficients` loop, which copies two
read-only `0x300`-byte tables into the accelerator and ultimately into the two
32-record firmware banks. Only records 7, 8, and 28 in either source are
nonzero; the analyzer resolves both PC-relative source addresses and emits all
72 signed 16-bit coefficients. Vinix populates those six records after
clearing the allocation, preserving zero for the other 58 records.

The pointer at `0x638` is not an extra I/O mapping. G17 vtable slot `0xe90`
resolves to `getBorderColorTableGPUAddress`, whose selected implementation is
the checked `bti; mov x0, #0; ret` stub, so the host explicitly publishes a
zero border-color-table address. Within the scalar block at `0xe90..0xfc3`,
two read-only vectors and direct literals establish ten nonzero startup words.
An eleventh word is feature-derived but deterministic: G17 vtable slot
`0x958` selects the G17 `configureDevice` implementation, its direct PI_300
base call unconditionally ORs feature bit 10 into accelerator field `0x6d0`,
and `initFirmwareData` extracts that bit into `0xec0`. The resulting values are
`0xeb8=1`, `0xec0=1`, `0xec8=1`, `0xed0=24000`, `0xed4=1`, `0xee0=1`, `0xee4=1`,
`0xee8=1`, `0xf04=31`, `0xf34=1`, and `0xf38=1`. The `0xed4` value is the
normal path selected by the driver's initially disabled debug flags. Vinix
populates these checked values while leaving the other feature-derived scalar
words gated. The adjacent `0xed8` word is not a literal: the base
`configureDevice` reads `gpu-power-sample-period` into accelerator offset
`0xf84c`, G17 vtable slot `0xf70` selects a getter that returns the cached word
unchanged, and `initFirmwareData` publishes it at `0xed8`. Vinix follows the
same path from the boot DeviceTree; the live Mac17,6 value is `8`.

The G17C accelerator vtable selects a 19-entry PIO relative-offset table.
Twelve entries use the primary SGX `IODeviceMemory` aperture and become
firmware records; the other seven take host-only alternate paths. The
firmware records are `{physical, virtual, total_size, element_size,
relative_offset, flags, padding}`. Their indices and primary aperture ranges
are:

| Record | SGX offset | Bytes |
|---:|---:|---:|
| 17 | `0x000000` | `0x21500` |
| 47 | `0x023d00` | `0x200` |
| 26 | `0xd04000` | `0x8000` |
| 29 | `0xd10000` | `0x4000` |
| 31 | `0xd40000` | `0x4000` |
| 33 | `0xd44000` | `0x4000` |
| 34 | `0xd4c000` | `0x200` |
| 28 | `0xd50000` | `0x10000` |
| 32 | `0xd60000` | `0x20000` |
| 35 | `0xe00000` | `0x4000` |
| 37 | `0xe40000` | `0x4000` |
| 43 | `0xe60000` | `0x58` |

Each source descriptor has count one and flag bit 1 set, so total and element
sizes match and the later `createFWPIOMapping` call requests a writable map.
Vinix now takes the translated SGX base and aperture size from the boot
DeviceTree, validates every range, and constructs these 12 initial records.
`createFWPIOMapping` aligns each physical base down to 16 KiB, rounds the
physical end up, and preserves the original low-page offset. Its second stage
tags the mapping with GART range 10 and writable option 7. The accelerator's
checked GART table defines range 10 as the 20 MiB canonical-high interval
`0xfffffc2180000000..0xfffffc2181400000`. During `initFirmwareData`, the host
gets each mapping's GPU VA, adds the saved physical-page offset, passes it
through G17C's identity firmware-address converter, and writes the result to
the record's `virtual_address` field.

Vinix now maps all 12 records into that range using firmware-only device
PTEs, retains sub-page offsets in their published addresses, and leaves a
fault-catching 16 KiB guard between independent mappings. A partial failure
unmaps the already installed prefix. The recovery tool validates the G17
vtable targets, complete PIO table, source-record construction, physical
alignment path, GART aperture, mapping options, and final firmware-record
publication. This completes PIO mapping but does not open the G17 boot gate;
the unrelated opaque hardware-configuration producers below remain required.

`fw.G17HardwareConfig` now represents those independently checked record
boundaries. Most scalar meanings are still unknown, so the remaining spans
stay opaque rather than receiving speculative names. The firmware-visible
regions currently proven include:

| Offset | Bytes | Observed use |
|---:|---:|---|
| `0x08f0` | 8 | fixed address load |
| `0x0e90..0x0e9f` | `0x10` | SoC chip ID and revision record |
| `0x0e90..0x0fc3` | `0x134` | scalar-control loads |
| `0x0fc4` | 4 | maximum performance-state index (`count - 1`) |
| `0x0fc8..0x1987` | `0x9c0` | frequency, voltage, and derived table region |
| `0x1988..0x19c7` | `0x40` | AFR relative boost-frequency table |
| `0x19c8..0x1a47` | `0x80` | complete vector copy |
| `0x1a48..0x1b8f` | `0x148` | CS clock-domain performance states |
| `0x1b90..0x1cd7` | `0x148` | AFR clock-domain performance states |
| `0x2540..0x270f` | `0x1d0` | late scalar, address, and byte controls |

These are access boundaries, not proof that the untouched bytes inside each
range are meaningful. Host-side construction still has to be modeled before
the allocation is safe to send to the GPU.

The leading scalar record is now independently reproduced. Apple's selected
`retrieveChipInfo` method reads `chip-id` from `/chosen` and `chip-revision`
from `/arm-io`, then emits `{chip_id, revision >> 4, revision & 7, 0}`. The
ARM firmware-data producer copies that 16-byte record to `0xe90`. The live
Mac17,6 values are `{0x6050, 1, 1, 0}`, and Vinix now reads them from the same
DeviceTree properties instead of embedding the observed revision.

The native `perf-states` and `perf-states-sram` properties use Apple
little-endian `{frequency_hz, voltage_mv}` records rather than standard
big-endian FDT cells. On this machine they contain four tables of 14 states;
the maximum core frequency is 1620 MHz. Vinix now validates those dimensions,
cross-checks the frequencies between core and SRAM tables, and can populate
the recovered primary frequency, secondary SRAM frequency, and 16-column
voltage regions. The host reads the two frequency arrays at accelerator
offsets `0x1b318` and `0x1bb60`, applies the same reciprocal Hz-to-MHz
conversion, and writes hardware-config tables `0xfc8` and `0x1808`; Vinix now
reproduces both. The table at `0x1908` is also fully DeviceTree-backed: the
host parses `gpu-perf-base-pstate`, clears all entries, and records each boost
state as `100 * (frequency - base) / (maximum - base)`. On this Mac the base
state is 1 and the final entry is 100. Vinix now reproduces this relative
boost-frequency table. The host constructs a second curve at `0x1988` from
the AFR-domain state array using the same base index and normalization. The
named AFR fast-die producer independently anchors that source at accelerator
offsets `0x1c4e8`/`0x1c4f0`; Vinix reproduces the live 14-state curve, ending
at 100. The remaining power-model-dependent tables stay gated.

The G17-only `cs-perf-states` and `afr-perf-states` properties use a distinct
64-bit format: `{rail_count, state_count}`, followed by
`{voltage_uV, frequency_hz}` records for every rail and state, then one default
SRAM voltage per rail. Apple's producer divides voltages by 1000 and clamps
each SRAM voltage to `max(core_mv, default_sram_mv)`. Both live M5 Max records
have one rail, 14 states spanning 24 MHz through 1620 MHz, and a 775 mV SRAM
floor. The selected G17C `getPerfStateCap` method returns 14 for both domains.
The host copies the normalized tables into two typed `0x148`-byte hardware
configuration blocks at `0x1a48` (CS) and `0x1b90` (AFR); Vinix now validates
and reproduces both complete blocks.

### UAT handoff

The symbolized `AGXUnifiedAddressTranslator::initHandoff` routine establishes
the complete `0x648`-byte G17 uPPL handoff initialization. It writes magic
`0x4b1d000000000002` at `0x00`, clears byte locks at `0x10` and `0x11`, clears
the turn word at `0x14`, initializes the current slot at `0x18` to
`0xffffffff`, and clears 65 `0x18`-byte flush records beginning at `0x20`.
If the firmware magic at `0x08` differs, it writes byte `1` at `0x638`; the
tail qword at `0x640` is cleared. The G17 path does not wait for firmware to
mirror the magic as the older Linux-derived Vinix path did.

Vinix now selects this initialization by firmware ABI. G13 retains its
existing handshake, and T6050 remains blocked from hardware writes until the
remaining G17 bootstrap allocations and power sequence are implemented.

The active boot kernel collection contains arm64e fileset entries for
`com.apple.AGXG17X` (UUID `680ACC23-AB13-301C-B28A-3A2A257F7977`) and the G17
firmware buddy (UUID `93F44AA7-63B3-3D75-8A9E-E4095ABBDD1D`). The former has
6,545 symbols, including named firmware allocation, initialization, UAT, and
channel routines. `extract_fileset.py` unwraps the local IMG4/LZFSE collection
and rebases its collection-relative segments and shared symbol table into
standalone Mach-Os. No Apple executable is committed.

## Upstream implementation boundary

The Apple Silicon kernel, bootloader, and Mesa trees audited on 2026-09-04 do
not implement this GPU:

- Linux Asahi `asahi` at `77cb8f2` and `gpu-next` at `84850f2` select G13/G14,
  not T6050/G17.
- m1n1 at `940439` recognizes T6050 as an SoC but its GPU boot handoff supports
  only T8103, T60xx, and T602x families.
- Mesa at `dc886f3` contains a newer `AGX2.xml` ISA description, but its Asahi
  device selection still covers G13/G14 and the official DRM UAPI does not
  match Vinix's provisional private ioctl layout.

Accordingly, `t6050_config()` is a discovery configuration and
`can_boot_firmware()` returns false. Removing that gate before implementing
and validating the G17 firmware, UAT/DART, power-handoff, and command ABIs is
not a supported bring-up step.
